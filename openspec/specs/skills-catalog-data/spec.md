# skills-catalog-data Specification

## Purpose

Обеспечивает получение каталога скиллов и одного скилла реальными данными из хранилища Supabase вместо статичных mock-данных, сохраняя существующую форму HTTP-ответа и параметры фильтрации.

## Requirements

### Requirement: Список скиллов читается из Supabase

Система SHALL возвращать по `GET /skills` список скиллов, прочитанный из таблицы `skills` в Supabase, в форме, соответствующей текущей generated-схеме `GetSkills200` (`id`, `title`, `questionsCount`, `difficulty`, `topic`, `core`).

#### Scenario: Список без фильтров

- **WHEN** клиент запрашивает `GET /skills` без query-параметров
- **THEN** система возвращает все строки таблицы `skills`, каждая в форме `{ id, title, questionsCount, difficulty, topic, core }`

#### Scenario: Пустая таблица

- **WHEN** в таблице `skills` нет ни одной строки
- **THEN** система возвращает пустой массив `[]` со статусом 200 (не ошибку)

### Requirement: Фильтрация каталога по параметрам контракта

Система SHALL применять фильтры `search`, `topic`, `difficulty`, `minQuestionsCount`, `maxQuestionsCount`, `core`, переданные в `GET /skills`, к данным Supabase так, чтобы результат совпадал с семантикой этих параметров.

#### Scenario: Фильтр по подстроке в названии

- **WHEN** передан `search=Замыкания`
- **THEN** возвращаются только скиллы, чей `title` содержит подстроку "Замыкания" (регистронезависимо)

#### Scenario: Фильтр по теме

- **WHEN** передан `topic=JavaScript`
- **THEN** возвращаются только скиллы с точным совпадением `topic = "JavaScript"`

#### Scenario: Фильтр по сложности

- **WHEN** передан `difficulty=medium`
- **THEN** возвращаются только скиллы с `difficulty = "medium"`

#### Scenario: Фильтр по направлению

- **WHEN** передан `core=frontend`
- **THEN** возвращаются только скиллы с `core = "frontend"`

#### Scenario: Фильтр по диапазону количества вопросов

- **WHEN** переданы `minQuestionsCount=5` и `maxQuestionsCount=20`
- **THEN** возвращаются только скиллы, у которых `questionsCount` находится в диапазоне `[5, 20]` включительно

#### Scenario: Комбинация фильтров без совпадений

- **WHEN** переданная комбинация фильтров не соответствует ни одной строке таблицы
- **THEN** система возвращает пустой массив `[]` со статусом 200

### Requirement: Деталь скилла читается из Supabase

Система SHALL возвращать по `GET /skills/{id}` один скилл из таблицы `skills` в Supabase, в форме, соответствующей generated-схеме `GetSkillById200` (`title`, `questions`, `core`), либо ответ 404, если скилл с таким `id` отсутствует. Для запроса с действующей сессией ответ SHALL дополняться признаком `completed` — отметкой этого пользователя об изучении скилла; для анонимного запроса признак SHALL отсутствовать. Так как ответ зависит от пользователя, он SHALL NOT кэшироваться.

#### Scenario: Существующий скилл

- **WHEN** клиент запрашивает `GET /skills/{id}` с `id`, существующим в таблице `skills`
- **THEN** система возвращает 200 с объектом `{ title, questions, core }`, соответствующим строке с этим `id`

#### Scenario: Отсутствующий скилл

- **WHEN** клиент запрашивает `GET /skills/{id}` с `id`, отсутствующим в таблице `skills`
- **THEN** система возвращает 404 без данных скилла

#### Scenario: Существующий скилл для авторизованного пользователя

- **WHEN** авторизованный пользователь запрашивает `GET /skills/{id}` с существующим `id`
- **THEN** система возвращает 200 с объектом `{ title, questions, core, completed }`, где `completed` — отметка этого пользователя об изучении скилла

#### Scenario: Ответ детали скилла не кэшируется

- **WHEN** выполняется запрос `GET /skills/{id}`
- **THEN** ответ содержит директиву, запрещающую кэширование

### Requirement: Ключи доступа к Supabase не раскрываются клиенту

Система SHALL выполнять все запросы к Supabase только на сервере (Route Handler или Server Component), не передавая URL и ключи Supabase в браузер и не делая их наблюдаемыми в client-side network-запросах.

#### Scenario: Браузерный запрос не содержит Supabase-адрес

- **WHEN** клиентский компонент вызывает `GET /skills` через сгенерированный React Query hook
- **THEN** сетевой запрос браузера направлен на собственный домен приложения (Route Handler), а не на домен Supabase, и не содержит Supabase service role key ни в URL, ни в заголовках

### Requirement: SSR прогревает клиентский кэш данными из Supabase

Система SHALL при серверном рендеринге раздела каталога и страницы скилла получать данные напрямую из Supabase (минуя собственный HTTP Route Handler) и прогревать TanStack Query cache так, чтобы гидратация на клиенте не приводила к повторному сетевому запросу за теми же данными.

#### Scenario: SSR каталога не делает self-fetch

- **WHEN** страница `/catalog/{core}` с наполненным разделом рендерится на сервере
- **THEN** данные каталога получены прямым вызовом серверного репозитория скиллов с фильтром по этому направлению, а не HTTP-запросом к `/api/skills` этого же приложения

#### Scenario: Гидратация переиспользует прогретые данные

- **WHEN** страница `/catalog/{core}` или `/catalog/{core}/{id}` открыта в браузере сразу после SSR-рендера
- **THEN** клиентский React Query hook получает данные из гидратированного кэша без дополнительного сетевого запроса при первом рендере

#### Scenario: Раздел в разработке не запрашивает список

- **WHEN** страница `/catalog/{core}` для направления без навыков (`backend`, `devops`, `design`) рендерится на сервере
- **THEN** запрос списка скиллов не выполняется ни на сервере, ни при гидратации

#### Scenario: SSR дашборда не делает self-fetch

- **WHEN** главная страница `/` рендерится на сервере
- **THEN** данные для сводных показателей получены прямым вызовом серверного репозитория скиллов, а не HTTP-запросом к `/api/skills` этого же приложения
