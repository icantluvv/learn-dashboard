## Context

Мотивация — см. `proposal.md - Why`. Существенное для дизайна:

- `app/manifest.ts` уже существует как Next `MetadataRoute.Manifest` и отдаётся по
  `/manifest.webmanifest` — Next сам добавляет `<link rel="manifest">`, отдельная разметка не нужна.
- Каталога `public/` в проекте нет вообще: ни одной статики, ни фавиконки. Плейсхолдер логотипа —
  серый квадрат в `src/components/navigation/logo.tsx`.
- `app/layout.tsx` уже объявляет `viewport: { viewportFit: 'cover' }`, а нижняя навигация
  учитывает `env(safe-area-inset-bottom)` — требование про системный индикатор в standalone уже
  выполнено предыдущим change'ем, здесь оно только фиксируется в спеке.
- Приложение тёмное по умолчанию на устройствах с тёмной темой (`--background: #1c2637`), в
  светлой — `#f1f1f3`.
- Тесты: browser-проект Vitest на реальном Chromium, Playwright E2E против dev-сервера.
- `sharp` уже присутствует в дереве зависимостей (перечислен в `allowScripts` корневого
  `package.json`) — Next использует его для оптимизации изображений.

## Goals / Non-Goals

**Goals:**

- Сделать приложение устанавливаемым по критериям браузеров: валидный манифест, существующие
  иконки, standalone-запуск на iOS и Android.
- Дать пользователю явную точку входа в установку, одинаково полезную и там, где есть API
  установки, и в iOS Safari, где его нет.
- Не навязываться: баннер закрывается и не возвращается.

**Non-Goals:**

- Service worker, офлайн-режим, кэширование и push-уведомления. Это отдельная тема с собственными
  рисками (устаревший кэш, невидимые обновления), и без неё приложение всё равно устанавливается.
- Настоящий фирменный логотип и брендинг — рисуется техническая марка, заменяемая одним файлом.
- Скриншоты и `shortcuts` в манифесте (богатая карточка установки в Android) — добавится, когда
  появится дизайн.

## Decisions

### 1. Иконки генерируются из SVG скриптом, в репозиторий попадают и исходник, и PNG

**Решение**: `public/icon.svg` — исходник марки; `scripts/generate-icons.ts` растрирует его через
`sharp` в `public/icon-192.png`, `public/icon-512.png`, `public/icon-maskable-512.png` и
`public/apple-touch-icon.png` (180×180). Все файлы коммитятся. Скрипт запускается вручную
(`npm run icons`), не на каждой сборке.

**Почему**: манифест обязан ссылаться на реально существующие файлы, а PNG нужны потому, что iOS до
сих пор не принимает SVG в `apple-touch-icon`. Генерация скриптом, а не «нарисовано руками в
редакторе», означает, что при замене марки все размеры пересоберутся согласованно. Коммит
результата, а не генерация в build, оставляет сборку детерминированной и не добавляет `sharp` в
критический путь CI.

**Альтернативы**:

- `app/icon.tsx` / `app/apple-icon.tsx` (ImageResponse) — Next генерирует иконки на лету из JSX.
  Отклонено: иконки становятся серверными маршрутами, каждый запрос — рендер, а содержимое иконки
  живёт в коде вместо ассета, который дизайнер может заменить.
- Только SVG без PNG — отклонено: iOS проигнорирует.

### 2. Маскируемая иконка — отдельный файл, а не тот же PNG с двумя `purpose`

**Решение**: `icon-512.png` объявляется как `purpose: any`, отдельный `icon-maskable-512.png` — как
`purpose: maskable`, и у него марка уменьшена внутрь безопасной зоны (80% полотна).

**Почему**: Android обрезает маскируемую иконку под форму, заданную устройством (круг, сквиркл,
капля). Один и тот же файл в обеих ролях означает либо обрезанные края у маскируемой, либо лишние
поля у обычной.

### 3. Логика видимости баннера — чистая функция, отделённая от React

**Решение**: `src/components/pwa-install/should-show-install-banner.ts` — функция от явного
состояния (`isStandalone`, `isDismissed`, `hasInstallPrompt`, `isIosSafari`) к решению
`'prompt' | 'ios-instructions' | 'hidden'`. Компонент только собирает это состояние из браузера.

**Почему**: комбинаций четыре штуки, и они плохо тестируются через DOM (эмулировать standalone или
`beforeinstallprompt` в component-тесте можно, но каждая ветка — отдельный рендер). Чистая функция
покрывается таблицей решений в unit-тесте, а component-тест проверяет только то, что компонент
показывает и делает.

### 4. Определение iOS Safari — по отсутствию API, а не только по user-agent

**Решение**: инструкция для iOS показывается, когда выполняются оба условия: `beforeinstallprompt`
не приходил и браузер похож на iOS Safari (`navigator.standalone` определён — признак Safari на
iOS). Ожидание события ограничено небольшим таймаутом после монтирования.

**Почему**: user-agent на iOS одинаков у Safari, Chrome и Firefox, но добавить на домашний экран
умеет только Safari; в остальных пункта «На экран „Домой"» нет. `navigator.standalone` —
нестандартное свойство, которое объявляет именно Safari на iOS, поэтому оно различает эти случаи
точнее, чем разбор строки user-agent. Само событие `beforeinstallprompt` приходит асинхронно, уже
после первого рендера, — отсюда таймаут, иначе инструкция мелькнёт в Chrome до прихода события.

**Альтернативы**: парсинг user-agent — отклонён как хрупкий и дающий ложные срабатывания в
iOS-Chrome; показывать инструкцию всем, у кого нет события, — отклонено: в desktop Firefox,
который не поддерживает установку вовсе, инструкция про «Поделиться» бессмысленна.

### 5. Отказ хранится в `localStorage`, а не в cookie

**Решение**: ключ `pwa-install-dismissed`, значение — отметка времени. Чтение — только на клиенте,
после монтирования.

**Почему**: это чисто клиентское, некритичное предпочтение, серверу оно не нужно ни для рендера, ни
для логики; cookie ушла бы в каждый запрос. Чтение после монтирования, а не при рендере, —
потому что на сервере `localStorage` нет, и попытка учесть его в первом рендере даёт
несовпадение разметки при гидратации.

**Компромисс**: отказ не переносится между браузерами и стирается при очистке данных сайта. Для
баннера установки это приемлемо.

### 6. Баннер живёт в `Layout` рядом с нижней навигацией

**Решение**: `PwaInstallBanner` — клиентский компонент, который `Layout` рендерит перед
`BottomNav`. На мобильной ширине — полоса во всю ширину над навигацией
(`fixed bottom-[calc(...)]`), на десктопе — карточка в правом нижнем углу. Внутри общий `Card`/
`Button` из `@repo/core`.

**Почему**: баннер должен быть виден на любом маршруте, а `Layout` — единственная точка, общая для
всех. Привязка к нижней навигации решает вопрос наложения: баннер поднимается ровно на высоту
панели и не перекрывает её.

## Test strategy

- **Static**: `npm run verify:fast` (`fmt:check`, `lint`, `tsc`), `npm run build` — манифест
  участвует в сборке.
- **Unit**: `should-show-install-banner.unit.test.ts` — таблица решений по четырём входам:
  standalone, закрыт, есть промпт, iOS Safari; плюс граничные комбинации (standalone + есть промпт
  → скрыт; закрыт + iOS → скрыт).
- **Component**: `pwa-install-banner.component.test.tsx` — кнопка вызывает сохранённый промпт;
  после закрытия баннер исчезает и в `localStorage` появляется отметка; в режиме iOS показывается
  инструкция и нет кнопки установки; при `standalone` не рендерится ничего.
- **Integration**: отдельного слоя нет — взаимодействие с браузерным API покрыто component-тестом
  через подставной объект события.
- **E2E**: `pwa.spec.ts` — `/manifest.webmanifest` отдаёт валидный JSON с непустыми полями и
  `display: standalone`; каждый файл иконки из манифеста и `apple-touch-icon` отвечает `200` с
  типом изображения; HTML содержит ссылку на манифест.
- **Performance**: не требуется; иконки — статические файлы, вес каждой проверяется глазами при
  генерации.
- **Manual**: установка на реальном iPhone через Safari и на Android/десктопе через Chrome; запуск
  с домашнего экрана в standalone; проверка, что внутри установленного приложения баннера нет;
  внешний вид иконки под маской на Android.

## Risks / Trade-offs

- **[Баннер раздражает]** → показывается один раз до закрытия, закрытие запоминается; внутри
  установленного приложения не показывается вовсе.
- **[Ложная инструкция для iOS в не-Safari браузерах]** → признаком служит `navigator.standalone`,
  а не user-agent; в остальных браузерах без события установки баннер просто скрыт.
- **[Мелькание баннера до прихода `beforeinstallprompt`]** → до истечения таймаута ожидания
  баннер не рендерится вообще.
- **[Иконка-заглушка уедет в продакшен как финальная]** → это техническая марка, и `proposal.md`
  прямо фиксирует, что она заменяется одним файлом; после замены достаточно перезапустить
  `npm run icons`.
- **[`sharp` как зависимость скрипта]** → скрипт не участвует в сборке и CI; если `sharp` окажется
  недоступен, пересборка иконок просто откладывается, приложение продолжает работать на
  закоммиченных PNG.
- **[Отсутствие service worker]** → браузеры устанавливают приложение и без него; офлайн-режима не
  будет, и это зафиксировано как Non-Goal, чтобы не выглядело упущением.
