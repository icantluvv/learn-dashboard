## Context

См. `proposal.md - Why`. Ключевое ограничение: в приложении нет ручного переключателя темы — есть
только `@custom-variant dark (&:is(.dark *))` (никогда не срабатывает, `.dark` нигде не проставляется
в коде) и `@media (prefers-color-scheme: dark)` в `app/globals.css`, который до этого change
переопределял только `--background`/`--foreground`. Все цвета заданы через CSS custom properties в
`:root`, подключённые к Tailwind v4 через `@theme inline`.

## Goals / Non-Goals

**Goals:**

- Единая точка правды для тёмных значений — `app/globals.css`, без разбросанных
  `dark:`-Tailwind-модификаторов (которые не работают без `.dark`-класса).
- Именованные токены (`--heading`, `--outline-*`, `--select-*`, `--slider-*`) вместо литеральных
  `bg-[#131313]`/`text-black`/`text-gray-500` в компонентах — упрощает будущий пересмотр палитры.
- `Select` и `InputGroup` остаются на фиксированной белой поверхности в обеих темах (осознанное
  решение, а не баг): это поверхности с плотным текстом/иконками, где инверсия усложняет контроль
  контраста без ощутимой пользы.

**Non-Goals:**

- Ручной переключатель темы (toggle, cookie/localStorage persist) — вне рамок этого change.
- Полный аудит тёмной темы для всего приложения — затронуты только компоненты, перечисленные в
  `proposal.md - Impact`.
- Изменение публичного API компонентов `@repo/core` (props, forwardRef-контракты) — только
  className/CSS.

## Decisions

- **CSS custom properties + `@theme inline`, а не Tailwind `dark:` variant.**
  Tailwind v4 `dark:` в этом проекте сконфигурирован как `&:is(.dark *)`, а `.dark` никогда не
  добавляется на `<html>`/`<body>`. Поэтому вся тёмная тема реализована через
  `@media (prefers-color-scheme: dark) { :root { --token: value; } }` — переопределение значений
  custom properties, от которых зависят Tailwind-утилиты, а не через `dark:`-префиксы в JSX.
  Альтернатива (завести `next-themes` и класс `.dark`) была бы более гибкой (ручной тоггл), но это
  отдельная фича с собственным UX и вне рамок текущего запроса.

- **Отдельные новые токены вместо переиспользования существующих семантических.**
  Для outline-кнопки, `Select` и `Slider` заведены собственные токены (`--outline-border`,
  `--select-background`, `--slider-track` и т.д.), а не переиспользование `--primary`/`--muted`/
  `--input` напрямую. Причина: у этих семантических токенов уже есть собственные обязанности в
  других компонентах (`Card`, `Popover`, `Badge` и т.д.), и их пришлось бы менять с оглядкой на все
  остальные потребители. Выделенные токены позволяют точечно настроить конкретный компонент, не
  трогая остальную палитру.

- **`Select`/`InputGroup` — фиксированные (не тематизированные) `--select-*` токены.**
  В отличие от `--outline-*`/`--slider-*`, у `--select-background`/`--select-foreground`/
  `--select-placeholder` одинаковые значения в `:root` и в `@media (dark)` (белый фон, `#171717`
  текст, `#6b7280` плейсхолдер) — то есть эти поверхности сознательно не инвертируются. Решение
  принято по прямой обратной связи в ходе работы: тёмный вариант с прозрачным/тёмным фоном и
  переменным по теме `--muted-foreground` давал слишком низкий контраст для плейсхолдера и текста.

- **Удаление мёртвых `dark:`-классов вместо их сохранения.**
  В `Button`/`Select`/`InputGroup` были классы вида `dark:bg-input/30`, `dark:border-input`,
  `dark:hover:bg-input/50`, доставшиеся от shadcn-шаблона. Поскольку `.dark`-класс никогда не
  применяется, эти классы были мёртвым кодом, создающим ложное впечатление, что тема уже
  обрабатывается для этих состояний. Они удалены, а не оставлены "на будущее" — не соответствовало
  бы `AGENTS.md` (не плодить неиспользуемый код, не готовить инфраструктуру заранее).

## Risks / Trade-offs

- [Другие, не перечисленные в `proposal.md - Impact`, компоненты приложения могут остаться
  нетематизированными (используют `bg-white`/`text-gray-*` напрямую)] → не блокирует этот change:
  зафиксировано как известное ограничение в `proposal.md - Impact`; последующие правки должны
  переиспользовать уже введённые токены (`text-heading`, `text-muted-foreground` и т.д.), а не
  создавать новые литералы.
- [`--outline-active-*` в тёмной теме использует `oklch(1 0 0 / 20%)` поверх произвольного фона под
  кнопкой — при очень светлом фоне под полупрозрачной кнопкой контраст текста/бордера может
  снизиться] → ограничено сценарием (тёмная тема всегда рисует тёмный `--background`/`--card` под
  такими кнопками), риск принят.
- [Ручной QA в браузере с `prefers-color-scheme: dark` необходим, так как автотесты не рендерят
  реальные вычисленные CSS-цвета в headless Chromium по умолчанию с эмуляцией цветовой схемы] →
  описано как Manual check в `test-plan.md`.

## Migration Plan

Чисто фронтенд CSS/className изменение, без миграции данных или API. Раскатка — обычный деплой.
Откат — `git revert` коммита(ов) change; отдельного флага не требуется, так как поведение полностью
управляется CSS и не имеет server-side или persisted-состояния.
