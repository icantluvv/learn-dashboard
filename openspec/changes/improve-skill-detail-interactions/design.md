## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Здесь фиксируются ограничения текущего кода,
которые определяют форму решения.

- Контракт приложения живёт в `api/src/openapi.yaml` (OpenAPI 3.0.2, `$ref` на `paths/` и
  `components/schemas/`), из него Kubb генерирует типы, zod-схемы, client, faker-фабрики,
  mock-routes и React Query хуки в `packages/api/base/codegen/**`. Generated-код не редактируется
  руками: `output.clean: true` удалит правки.
- Навыки не имеют внешнего бэкенда: `GET /api/skills` и `GET /api/skills/{id}` обслуживаются Route
  Handlers этого же приложения, а `packages/api/base/client.ts` через `isSameOriginPath` уже
  считает same-origin любой путь, начинающийся на `/api/skills/` — новый вложенный путь
  `/api/skills/{id}/completion` попадает под это правило без изменений клиента.
- Чтение навыков идёт через PostgREST (`@repo/api/database`, service-role ключ, только GET
  операции в `api/src/database/openapi.yaml`). Записи данных пользователя уже делаются напрямую
  через пул `pg` (`src/lib/auth/database.server.ts`, см.
  `src/modules/auth/avatar-repository.server.ts`).
- Счётчик `user."completedSkillsCount"` существует (миграция `20260927090000`), объявлен в
  Better Auth как `additionalFields` с `input: false` и читается `getCurrentUser()`; дашборд
  главной страницы берёт его из `GET /api/dashboard-stats`. Сейчас его никто не увеличивает.
- `getSkillById` в `src/modules/skills/server/skills-repository.ts` обёрнут в React `cache()` и
  используется и страницей, и `generateMetadata`. Он не должен зависеть от сессии: метаданные
  одинаковы для всех пользователей.
- Страница навыка — Server Component: она читает навык на сервере и прогревает клиентский кэш
  через `queryClient.setQueryData(getSkillByIdQueryOptions({ id }).queryKey, skill)`.
- `@repo/core` собран на Base UI (`@base-ui/react` 1.8.0) и shadcn-генерации (`components.json`,
  style `base-nova`, алиас `ui` → `@repo/core/src/ui`). Примитива `Tooltip` в пакете нет.
- Форма входа сейчас безусловно делает `router.replace('/')` после успеха.

## Goals / Non-Goals

**Goals:**

- Одна операция контракта покрывает и постановку, и снятие отметки, и её вызывает сгенерированный
  Kubb mutation-хук — без рукописного fetch-слоя.
- Отметка и счётчик не расходятся ни при какой последовательности запросов, включая повторные и
  параллельные.
- Состояние кнопки при первом рендере страницы приходит с сервера: без «мигания» из «не отмечено»
  в «отмечено».
- `Tooltip` появляется как переиспользуемый примитив пакета, а не как локальный компонент страницы.

**Non-Goals:**

- Отметки не показываются в каталоге и не участвуют в фильтрах (решение пользователя: scope —
  только страница навыка). `GET /api/skills` не меняется.
- Прогресс по отдельным вопросам, история изучения и даты в интерфейсе не показываются
  (`completed_at` в таблице хранится, но контрактом не отдаётся).
- Offline-режим и оптимистичная запись без сети не рассматриваются.
- Server Actions для этой операции не используются — см. решение 2.

## Decisions

### 1. Хранение: отдельная таблица отметок, счётчик пересчитывается из неё

`user."completedSkillsCount"` не может быть источником правды: по числу нельзя узнать, отмечен ли
конкретный навык. Добавляется таблица:

```sql
create table public.user_completed_skill (
	"user_id" text not null references public."user" ("id") on delete cascade,
	"skill_id" text not null references public.skills ("id") on delete cascade,
	"completed_at" timestamptz not null default now(),
	primary key ("user_id", "skill_id")
);
```

Composite primary key делает повторную отметку невозможной на уровне схемы (идемпотентность
операции получается бесплатно через `on conflict do nothing`), а `on delete cascade` убирает
отметки вместе с пользователем и вместе с удалённым навыком. RLS включается с deny-all политикой
для `anon`/`authenticated` — по образцу `skills` и `user_avatar`: таблица доступна только
серверному коду приложения.

Счётчик остаётся в `user`, но перестаёт быть независимой величиной: он пересчитывается из таблицы
тем же запросом, который меняет отметку.

_Альтернативы:_ массив `text[]` в `user` — не даёт FK на `skills` и плохо расширяется;
инкремент/декремент счётчика (`+1`/`-1`) — расходится при любом повторном запросе или частичной
ошибке; полный отказ от счётчика в пользу `count(*)` на каждый запрос дашборда — потребовал бы
менять `additionalFields` Better Auth, `getCurrentUser`, `GET /api/me`, `GET /api/dashboard-stats`
и спеку `home-dashboard`, то есть заметно больший diff ради устранения денормализации, которая
внутри одного SQL-запроса и так не может разъехаться.

### 2. Запись: `pg`-пул одним SQL-запросом, а не PostgREST и не Server Action

Отметку пишет Route Handler через `getAuthDbPool()` — тем же способом, которым уже пишется
`user_avatar`. Один запрос меняет отметку и пересчитывает счётчик, поэтому промежуточного
состояния «отметка есть, счётчик старый» не существует:

```sql
with changed as (
	insert into user_completed_skill ("user_id", "skill_id")
	values ($1, $2)
	on conflict do nothing
)
update "user"
set "completedSkillsCount" = (
	select count(*) from user_completed_skill where "user_id" = $1
)
where "id" = $1
returning "completedSkillsCount"
```

Снятие отметки — тот же запрос с `delete from user_completed_skill where "user_id" = $1 and
"skill_id" = $2` в CTE. Счётчик именно пересчитывается (`count(*)`), а не сдвигается: если
значение когда-то разъехалось, первая же операция его вылечит.

`PUT` на несуществующий навык нарушает FK на `skills` → это ловится по коду ошибки Postgres
`23503` и отдаётся как `404`; отдельный предварительный `select` из `skills` не нужен и создал бы
окно между проверкой и вставкой.

_Альтернативы:_ PostgREST-запись потребовала бы новых POST/DELETE операций в
`api/src/database/openapi.yaml` и двух round-trip (отметка + счётчик) без общей транзакции; триггер
в БД, поддерживающий счётчик, добавил бы неявную логику в схему при том, что приложение всё равно
делает запрос само. Server Action не используется, потому что запрос отправляет сгенерированный
Kubb хук: Server Action недоступен по HTTP-контракту, не имеет описания в OpenAPI и для него нельзя
сгенерировать ни клиент, ни mock, ни zod-схему ответа — пришлось бы писать вызов вручную, ровно то,
чего проектные правила требуют избегать.

### 3. Контракт: один `PUT` с булевым телом

```yaml
# api/src/paths/api_skills_id_completion.yaml
put:
    summary: Set skill completion for the current user
    operationId: setSkillCompletion
    tags: [Skills]
    security: [{ auth_cookie: [] }]
    requestBody: { completed: boolean } # required
    responses: 200 SkillCompletion, 400, 401, 404
```

`SkillCompletion` = `{ completed: boolean, completedSkillsCount: integer }` — клиент получает и
итоговое состояние кнопки, и новое значение счётчика, поэтому дашборд можно обновить без
дополнительного запроса.

Один `PUT` вместо пары `POST`/`DELETE`: переключатель по природе идемпотентен и выражается
целевым состоянием, а Kubb в этом случае генерирует один mutation-хук с типизированным телом
вместо двух хуков, которые страница обязана выбирать по текущему состоянию. `tags: [Skills]` —
чтобы операция попала в тот же сгенерированный контроллер, что остальные операции навыков.

Признак `completed` добавляется в `components/schemas/Skill.yaml` как необязательное поле с
описанием «present only for authenticated request» — тот же приём уже применён к
`DashboardStats.completedSkillsCount`, поэтому анонимный ответ остаётся валидным по схеме и
существующие потребители не ломаются.

### 4. Чтение отметки: композиция, а не изменение `getSkillById`

`getSkillById` остаётся не зависящим от сессии (его вызывает `generateMetadata`). Отметка читается
отдельной функцией нового репозитория:

```
src/modules/skills/server/skill-completion-repository.server.ts
  isSkillCompleted(userId, skillId): Promise<boolean>
  setSkillCompletion(userId, skillId, completed): Promise<number>  // новый счётчик
```

Композиция происходит в двух местах, которые и так знают о пользователе: в
`app/api/skills/[id]/route.ts` (обогащает JSON) и в `page.tsx` (подмешивает `completed` в объект,
которым прогревается клиентский кэш). Обе точки вызывают `getCurrentUser()`, уже обёрнутый в
`cache()`, — дополнительных чтений сессии на запрос не появляется.

`GET /api/skills/{id}` получает `Cache-Control: no-store` (как уже сделано в
`app/api/dashboard-stats/route.ts`): ответ стал пользовательским, и кэширование выдало бы отметку
одного пользователя другому. Ответ `404` остаётся без изменений.

### 5. Кнопка: клиентский лист с состоянием из прогретого кэша

`skill-completion-button.tsx` — Client Component в существующем
`app/(main)/catalog/[core]/[id]/_components/skill-detail/`. Логика:

- состояние берётся из `useGetSkillById({ id })` — данные уже в кэше после SSR-прогрева, поэтому
  первый рендер сразу правильный (требование «без мигания»);
- признак авторизации — `useGetAuthMe()`; для анонима компонент рендерит `next/link` на
  `/sign-in?next=<путь навыка>` вместо кнопки с обработчиком, так что клик физически не может
  отправить мутацию;
- мутация — `useSetSkillCompletion()` из `@repo/api`; на время `isPending` кнопка `disabled`
  (защита от двойного клика даёт ровно один запрос);
- `onSuccess`: `setQueryData` на ключ навыка с `completed` из ответа и
  `invalidateQueries` на ключ `getDashboardStatsQueryKey()`, чтобы счётчик дашборда подтянулся;
  `onError`: кэш не менялся, показывается `toast` из `@repo/core`;
- состояние выражается `aria-pressed`, а не только цветом; визуально — `variant` кнопки и иконка
  `Check` из `lucide-react`.

Оптимистичное обновление (`onMutate` + rollback) не делается: запрос к собственному Route Handler
быстрый, а `disabled`-состояние уже даёт обратную связь; откат добавил бы ветку, которую нужно
тестировать, без заметного выигрыша. Это причина, по которой спека требует «кнопка возвращается в
состояние до нажатия при ошибке» — при отсутствии оптимистичного апдейта это выполняется само.

### 6. Возврат после входа: `?next=` с валидацией на внутренний путь

Страница входа читает `next` из query. Валидация — общая функция (`src/modules/auth/`), которая
принимает строку и возвращает безопасный путь или `'/'`: требует ведущий `/`, отвергает `//`
(protocol-relative), любую схему, а также сами `/sign-in` и `/sign-up` (иначе после входа
пользователь снова попадает на форму). Проверка живёт в одном месте и покрывается unit-тестами на
граничные значения, потому что это защита от open redirect, а не косметика.

`SignInForm` получает уже провалидированный путь пропом от серверной страницы и делает
`router.replace(path)`. Форма регистрации в этом change не меняется.

### 7. `Tooltip` как примитив пакета

Примитив добавляется генерацией shadcn в `packages/core` (`npx shadcn@latest add tooltip` —
**npm/npx, не `bunx`**: в репозитории единственный пакетный менеджер — npm под Node.js 24, см.
`AGENTS.md`; `components.json` уже настроен на `@repo/core/src/ui` и style `base-nova`, то есть
генерация даёт обёртку над Base UI, а не Radix). Сгенерированный файл приводится к конвенциям
пакета (kebab-case директория `tooltip/`, `index.ts`, тонкая обёртка, `cn` для className) и
экспортируется из `packages/core/index.ts`. Рядом — component test на наведение/фокус/скрытие.

Кнопка копирования вопроса — тоже примитив-лист страницы (`copy-question-button.tsx`), а не часть
`SkillDetailContent`: у неё собственное состояние «скопировано» и обработка отказа
`navigator.clipboard`. Доступное имя задаётся `aria-label` (текст подсказки визуальный, но
`Tooltip` Base UI связывает подсказку с триггером программно).

## Risks / Trade-offs

- **Денормализованный счётчик в `user`** → пересчитывается из таблицы отметок в том же SQL-запросе,
  поэтому расхождение возможно только при прямых ручных правках БД; первая же операция отметки его
  исправляет.
- **`GET /api/skills/{id}` стал пользовательским** и теперь `no-store` → теряется возможность
  кэшировать деталь навыка на CDN. Осознанный размен: альтернатива (отдельный запрос состояния
  отметки) даёт второй round-trip и мигание кнопки. Сам контент навыка по-прежнему кэшируется на
  уровне рендера страницы.
- **Регенерация Kubb перезапишет `packages/api/base/codegen/**`** → после правки контракта
  обязательны `npm --workspace @repo/api run generate` и root `npm run tsc`; ручные правки
  generated-файлов запрещены и будут потеряны.
- **`navigator.clipboard` недоступен в незащищённом контексте (не `https`, не `localhost`)** →
  пользователь получает сообщение об ошибке вместо тихого молчания; fallback через
  `document.execCommand` не добавляется (deprecated, и продакшен работает по https).
- **`?next=` — потенциальный open redirect** → валидация на внутренний путь в одном общем месте
  плюс unit-тесты на граничные значения (`//host`, `https://host`, `/sign-in`, пустая строка).
- **Новая таблица ссылается на `skills` и на `user`** → миграция обязана применяться после
  существующих (порядок по timestamp в имени файла соблюдается); на стенде без применённой
  миграции операция вернёт ошибку хранилища, а кнопка — сообщение о неудаче, без падения страницы.
- **Число изученных навыков может превысить число доступных**, если навык удалён из каталога →
  `on delete cascade` по `skill_id` удаляет отметку вместе с навыком, и счётчик пересчитается при
  следующей операции пользователя; ретроспективный пересчёт для всех пользователей в scope не
  входит.

## Migration Plan

1. Применить миграцию `supabase/migrations/<ts>_create_user_completed_skill_table.sql` (создание
   таблицы + RLS deny-all). Обратная засыпка не нужна: существующие `completedSkillsCount` равны
   нулю, отметок ещё нет.
2. Обновить контракт и выполнить `npm --workspace @repo/api run generate`; закоммитить
   `api/src/**` и `packages/api/base/codegen/**` вместе.
3. Развернуть приложение. Порядок важен: код без таблицы вернёт ошибку хранилища на попытку
   отметки, поэтому миграция идёт первой.
4. **Rollback**: откат кода приложения достаточен — контракт обратно совместим, а новая таблица
   никем, кроме новой операции, не читается. Таблицу можно оставить; при необходимости полного
   отката — `drop table public.user_completed_skill` и `update "user" set
"completedSkillsCount" = 0`.

## Test strategy

Уровни выбираются по самому дешёвому слою, на котором поведение наблюдаемо; полное соответствие
сценариям спеки — в `test-plan.md`.

- **Static**: `npm run tsc` (включая generated-код), `npm run lint`, `npm run fmt:check`,
  `openspec validate --strict`.
- **Unit (Node)**: SQL-репозиторий отметок на замоканном пуле `pg` (идемпотентность, маппинг
  ошибки FK `23503` в `404`, возврат пересчитанного счётчика); Route Handler
  `PUT /api/skills/[id]/completion` (401 без сессии, 400 на некорректное тело, 404 на неизвестный
  навык, 200 с итоговым состоянием); `GET /api/skills/[id]` (наличие/отсутствие `completed`,
  заголовок `no-store`); валидация адреса возврата (`//host`, `https://host`, `/sign-in`, пустое
  значение, корректный путь); `isSameOriginPath('/api/skills/x/completion') === true`.
- **Component (реальный Chromium, `vitest-browser-react`)**: кнопка отметки — начальное состояние
  из кэша, переключение в обе стороны, `disabled` во время запроса и один запрос на двойной клик,
  возврат состояния и сообщение при ошибке, `aria-pressed`, ссылка на `/sign-in?next=…` для
  анонима; кнопка копирования — копирование текста ровно одного вопроса без номера, работа с
  клавиатуры, сообщение при отказе `clipboard`; `Tooltip` примитива — показ по наведению и фокусу,
  скрытие, сохранение действия триггера; обновлённый `SkillDetailContent` — цвет нумерации и
  увеличенный отступ проверяются через вычисленные стили, а не через сравнение снимков.
- **Integration**: страница навыка (`page.tsx`) прогревает кэш значением `completed` для
  авторизованного пользователя и без него — для анонима; `GET /api/dashboard-stats` отдаёт число,
  равное числу отметок, после операции отметки (репозитории замоканы).
- **E2E (Playwright, Chromium)**: сквозной путь авторизованного пользователя — открыть навык,
  отметить, перезагрузить (отметка сохранилась), увидеть увеличенный счётчик на главной, снять
  отметку, перезагрузить; путь гостя — клик по кнопке ведёт на `/sign-in`, после входа
  пользователь возвращается на страницу навыка и навык не отмечен.
- **Performance**: отдельных проверок нет; единственный новый запрос — один `PUT` по действию
  пользователя.
- **Manual**: копирование в буфер обмена в реальном браузере (Playwright требует отдельных
  разрешений на clipboard, и проверка вставки вне страницы автоматизации недоступна); подсказка
  «копировать вопрос» на touch-устройстве; визуальная проверка блока заголовка с длинным названием
  навыка на узком экране.
