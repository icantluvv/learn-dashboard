## Context

До этого изменения `app/(home)/page.tsx` напрямую вызывал `getSkills()` внутри одного серверного
компонента `Catalog` и рендерил статичный массив карточек — без фильтрации, без состояний
загрузки/ошибки/пустого результата, без связи с сайдбаром фильтров. Контракт `/api/skills` не принимал
параметров. Проект уже использует `@tanstack/react-query` (провайдер подключён в `app/layout.tsx`),
`nuqs` (адаптер подключён там же) и Kubb-кодогенерацию `@repo/api` поверх `api/src/openapi.yaml`. См.
`proposal.md - Why` для мотивации.

## Goals / Non-Goals

**Goals:**

- Дать пользователю фильтровать каталог по названию/теме/сложности/диапазону количества вопросов без
  перезагрузки страницы.
- Сохранить быстрый первый рендер: список без фильтров должен быть виден сразу после серверного
  рендера, без мигания скелетоном.
- Любое изменение фильтра должно приводить к новому запросу списка тем же, уже отлаженным, механизмом
  React Query — без ручной синхронизации состояния между сайдбаром и каталогом.
- Состояние фильтров должно быть в URL (переживает reload, шарится ссылкой).

**Non-Goals:**

- Реальный бэкенд не реализуется и не проверяется — поведение фильтрации описано и протестировано
  только для mock-режима (`packages/api/base/mock-scenarios.ts`).
- Страница `/catalog/{id}` в рамках этого изменения — только маршрут-заглушка; полноценная страница
  деталей навыка не в скоупе.
- Interaction-тесты на выбор значения в `Select`/`Slider` не добавлены (см. `test-plan.md -
Out of scope`).

## Decisions

### 1. Где выполняется первый запрос списка

**Решение**: `app/(home)/page.tsx` (server component) делает `queryClient.query(getSkillsQueryOptions())`
без фильтров и оборачивает дерево в `<HydrationBoundary state={dehydrate(queryClient)}>`. Клиентский
`Catalog` читает тот же query через `useGetSkills({ params })` — при пустых фильтрах ключ запроса
совпадает с серверным префетчем, и React Query отдаёт уже загруженные данные без повторного запроса и
без скелетона.

**Альтернативы**:

- Оставить `await getSkills()` внутри `Catalog` без React Query — самый простой вариант, но тогда
  смена фильтра на клиенте не могла бы переиспользовать этот же механизм загрузки/ошибки/кэша; пришлось
  бы вручную писать client-side fetch с своим состоянием, дублируя логику React Query.
- Держать `queryClient.prefetchQuery` внутри `Catalog`, а не в `page.tsx` — методологически ближе к
  "компонент владеет своими данными", но `prefetchQuery` в установленной версии `@tanstack/react-query`
  помечен deprecated в пользу `queryClient.query(...)`, и `page.tsx` уже является естественной границей
  server/client для маршрута.

### 2. Где хранится состояние фильтров

**Решение**: `app/(home)/_hooks/use-skills-filters.ts` — `useQueryStates` из `nuqs` на пяти парсерах
(`search`, `topic`, `difficulty`, `minQuestionsCount`, `maxQuestionsCount`), плюс `toSkillsQueryParams()`,
схлопывающий пустые/дефолтные значения в `undefined`, чтобы query key у `useGetSkills()` без активных
фильтров совпадал с ключом серверного префетча (`[{ url: '/api/skills' }]`).

**Альтернативы**:

- React Context или локальный `useState`, поднятый до общего родителя `SidebarFilters` + `Catalog` — не
  даёт персистентности при reload и не шарится ссылкой; создал бы дополнительный layer только ради
  прокидывания состояния между двумя ветками дерева.
- Zustand/другой внешний стор — избыточен, раз `nuqs` уже используется в проекте как единственный
  инструмент URL-стейта (см. `AGENTS.md`).

### 3. Как фильтр триггерит новый запрос

**Решение**: `Catalog` и все поля сайдбара читают/пишут в один и тот же `useSkillsFilters()`. Изменение
любого поля меняет `params`, переданный в `useGetSkills({ params })`, что меняет query key — React Query
сам инициирует рефетч. Никакого прямого вызова между `SidebarFilters` и `Catalog` нет.

**Альтернативы**:

- Явный callback/event bus между `SidebarFilters` и `Catalog` — работал бы, но заново реализует то, что
  React Query уже делает через query key, и плохо масштабируется при добавлении новых фильтров.

### 4. Где фильтрация реально происходит для тестов/dev

**Решение**: `packages/api/base/mock-client.ts` прокидывает `config` (включая `params`) в
`route.create(config)`; `packages/api/base/mock-scenarios.ts` получил `filterSkillCards()` — фильтрует
статичный список карточек по всем пяти параметрам (case-insensitive substring для `search`, точное
совпадение для `topic`/`difficulty`, диапазон для `minQuestionsCount`/`maxQuestionsCount`).

**Альтернативы**:

- Оставить мок игнорировать `params` (как было) — тогда смена фильтра действительно создаёт новый
  HTTP/mock-запрос (query key меняется), но результат всегда одинаковый, и фича выглядит нерабочей в
  единственном доступном сейчас режиме (mock).

## Risks / Trade-offs

- **[Риск]** Реальный backend может не поддерживать эти query-параметры так же, как mock → **Митигация**:
  контракт (`api/src/paths/api_skills.yaml`) — источник истины для backend-команды; параметры
  опциональны, обратной несовместимости нет.
- **[Риск]** Отсутствие покрытия `Select`/`Slider` component-тестами — регрессия в выборе значения не
  будет поймана автотестами → **Митигация**: зафиксировано в `test-plan.md - Out of scope` как
  осознанный gap, а не забытый случай.
- **[Риск]** `queryClient.query()` — сравнительно новый метод (заменяет deprecated `prefetchQuery`) →
  **Митигация**: обёрнут в `.catch(() => undefined)`, чтобы ошибка сети на сервере не роняла SSR-рендер
  страницы — ошибка всё равно попадает в гидратированный кэш и корректно показывается клиентом через
  `isError`.

## Test strategy

- **Unit**: чистая логика без DOM — `toSkillsQueryParams()` (сборка/схлопывание query-параметров) и
  `filterSkillCards` через мок-роут `GET /api/skills` (все пять фильтров + комбинации + пустой результат).
- **Component**: `SkillCard` (рендер полей, RU-лейбл сложности, ссылка), `Catalog` (все четыре ветки:
  loading/error/empty/success, через мокнутый `useGetSkills`), `ResetFiltersButton` (сброс URL через
  `NuqsTestingAdapter`).
- **Integration/E2E**: не добавлялись в это изменение — см. `test-plan.md - Out of scope` и
  `design.md - Risks` по `Select`/`Slider`.
- Подробная матрица покрытия — в `test-plan.md`.
