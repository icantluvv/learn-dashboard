## Context

Мотивация — см. `proposal.md → Why`. Требования — см. `specs/page-seo-metadata/spec.md`.

Технические ограничения, формирующие подход:

- Next.js 16.3.4, App Router. `metadata` и `generateMetadata` поддерживаются только в Server
  Components и взаимоисключающи в пределах одного сегмента.
- В `next.config.ts` включён `cacheComponents: true`. По документации Next.js
  (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md`,
  раздел «With Cache Components») `generateMetadata` подчиняется тем же правилам, что и остальные
  компоненты: если она читает runtime-данные или делает некешированный fetch, она откладывается на
  request time. Ошибка возникает только тогда, когда сама страница при этом полностью
  пререндерится. В нашем случае все динамические маршруты уже делают некешированные запросы в
  теле страницы (`getSkills`, `getSkillById`, `getCoreByType`, `getDashboardStats`,
  `getCurrentUser`), поэтому отдельный `DynamicMarker` не нужен.
- Все серверные репозитории (`src/modules/*/server/*-repository.ts`) помечены `server-only` и
  вызывают Hey API SDK. Ни одна функция сейчас не обёрнута в React `cache()`.
- Текущая структура маршрутов: `app/(auth)/{sign-in,sign-up}`, `app/(main)/(home)`,
  `app/(main)/catalog`, `app/(main)/catalog/[core]`, `app/(main)/catalog/[core]/[id]`,
  `app/(main)/profile`, плюс `app/not-found.tsx` и `app/(main)/not-found.tsx`.
- Реестр направлений — `src/constants/skill-cores.ts` (`SKILL_CORES`, `resolveSkillCore`),
  выведенный из OpenAPI-контракта. Названия и описания направлений для UI приходят из БД
  (`getCoreByType`), но эти данные недоступны без запроса.
- `NEXT_PUBLIC_FRONT_URL` уже обязателен в `src/env/client.ts` и используется в `robots.ts` и
  `sitemap.ts`.
- Архитектурные границы (`AGENTS.md`): shared-слой `src/*` может зависеть только от `packages/*`;
  `app/` может зависеть от `src/*`. Новый SEO-слой обязан лежать в shared, а не в `app/`.

## Goals / Non-Goals

**Goals:**

- Единственный источник правды для бренда и SEO-строк, из которого читают все маршруты, manifest
  и хелперы.
- Декларативные метаданные на маршрут: минимум кода в `page.tsx`, вся сборка `Metadata` — в одном
  хелпере.
- Отсутствие удвоенных сетевых запросов при добавлении `generateMetadata` на динамические
  маршруты.
- Совместимость с `cacheComponents: true` без отключения streaming metadata и без изменения
  `next.config.ts`.

**Non-Goals (уровня дизайна, дополнительно к scope из proposal):**

- Не вводится i18n-инфраструктура и `alternates.languages`, даже несмотря на смену `lang` на `ru`.
- Не вводится собственный кеш-слой поверх репозиториев: дедупликация ограничивается пределами
  одного запроса.
- Не меняется способ получения UI-названий направлений на самих страницах — SEO-строки для
  направлений задаются статически и не зависят от доступности БД.

## Decisions

### Решение 1. Отдельный shared-модуль `src/seo/` как источник правды

Создаётся `src/seo/` с публичным API через `index.ts`:

- `src/seo/brand.ts` — `BRAND_NAME` (`'StarSkills'`), `BRAND_SHORT_NAME`, `SITE_DESCRIPTION`,
  `TITLE_TEMPLATE` (`'%s — StarSkills'`), `OG_LOCALE` (`'ru_RU'`).
- `src/seo/cores.ts` — статический реестр SEO-строк по направлению: `{ title, description }` для
  каждого значения `SkillCore`. Тип — `Record<SkillCore, CoreSeoCopy>`, поэтому добавление
  направления в контракт ломает сборку, пока строка не добавлена.
- `src/seo/build-metadata.ts` — `buildPageMetadata({ title, description, path, noIndex })`,
  возвращающая `Metadata` с `title`, `description`, `alternates.canonical`, `openGraph` и
  `twitter`; `noIndex: true` добавляет `robots: { index: false, follow: false }`.
- `src/seo/urls.ts` — `absoluteUrl(path)` поверх `clientEnvironment.NEXT_PUBLIC_FRONT_URL`.

Модуль universal (без `server-only`): он не делает запросов и читает только client-env, что
позволяет переиспользовать `BRAND_NAME` в `manifest.ts` и при необходимости в UI.

_Почему не `src/constants/seo.ts`:_ нужны не только константы, но и хелпер сборки `Metadata` и
реестр по направлениям; это связный модуль, а не набор констант.

_Почему не `src/modules/seo/`:_ по `AGENTS.md` модуль — доменная логика для нескольких маршрутов;
SEO — инфраструктурный shared-слой без бизнес-сущностей, его потребитель — сам routing layer.

### Решение 2. `canonical` задаётся относительным путём, база — через `metadataBase`

В корневом layout задаётся `metadataBase: new URL(clientEnvironment.NEXT_PUBLIC_FRONT_URL)`.
`buildPageMetadata` кладёт в `alternates.canonical` и `openGraph.url` относительный путь
(`/catalog/frontend`), а Next.js резолвит его в абсолютный по `metadataBase`.

_Альтернатива:_ собирать абсолютные URL вручную в каждом месте. Отклонена: дублирует логику,
которую фреймворк уже выполняет, и легко разъезжается со слешами в конце пути.

Требование спеки «query-параметры не попадают в canonical» выполняется автоматически: путь
строится из `params`, а `searchParams` в `generateMetadata` не читается. Это же избавляет
`/catalog/[core]` от чтения `searchParams` и от лишнего перехода в runtime-режим.

### Решение 3. Шаблон заголовка в корневом layout, страницы задают только свою часть

Корневой layout:

```ts
title: { default: `${BRAND_NAME} — ...`, template: TITLE_TEMPLATE }
```

Страницы возвращают короткий `title` (`'Каталог направлений'`, `skill.title`), а суффикс с брендом
добавляет Next.js. Это выполняет требование «бренд присутствует в заголовке всех страниц» без
дублирования строки по маршрутам.

Ограничение фреймворка: `title.template` не применяется к самому сегменту, который его объявил,
поэтому у корневого layout обязателен `title.default`.

### Решение 4. Дедупликация данных через React `cache()` в репозиториях

`getSkillById` и `getCoreByType` оборачиваются в `cache()` из `react`. `generateMetadata` и
компонент страницы вызывают ту же функцию с теми же аргументами и получают один сетевой запрос на
один запрос страницы.

_Почему не полагаться на автоматическую мемоизацию `fetch`:_ запросы идут через Hey API SDK, и
гарантия мемоизации зависит от того, как именно клиент вызывает `fetch` и какие опции кеша
передаёт. Документация Next.js прямо рекомендует React `cache`, когда `fetch` недоступен как
точка мемоизации. Обёртка дешёвая и делает поведение явным.

_Почему не `'use cache'`:_ данные навыка не должны кешироваться между запросами без отдельного
решения о `cacheLife`/`cacheTag`; задача здесь — дедупликация внутри одного запроса, а не
кеширование.

Обёртка ставится в репозитории, а не в route-файле: иначе каждый маршрут заводил бы свою
`cache()`-обёртку и дедупликация перестала бы работать между `generateMetadata` и страницей.

### Решение 5. SEO-строки направлений статические, а не из БД

`generateMetadata` для `/catalog/[core]` берёт заголовок и описание из `src/seo/cores.ts`, а не
из `getCoreByType`.

_Почему:_ метаданные становятся независимы от доступности БД (требование спеки «недоступность
источника данных не ломает метаданные»), а на самом частом маршруте каталога не появляется
дополнительный сетевой запрос ради `<title>`. Названия направлений — стабильный маркетинговый
текст, меняющийся вместе с релизом, а не контент, редактируемый в БД.

_Следствие:_ при расхождении названия направления в БД и в SEO-реестре пользователь увидит в
заголовке вкладки строку из реестра. Принимается осознанно; типизация `Record<SkillCore, …>`
делает пропуск направления ошибкой сборки.

Для `/catalog/[core]/[id]` тот же приём неприменим — название навыка известно только из данных,
поэтому там `generateMetadata` обращается к `getSkillById` (см. Решение 4).

### Решение 6. Обработка ошибок и 404 в `generateMetadata`

- `resolveSkillCore(segment) == null` → `notFound()` прямо в `generateMetadata` (документация
  прямо разрешает `notFound()` и `redirect()` внутри неё).
- `getSkillById` бросает исключение → `generateMetadata` ловит его и возвращает fallback-метаданные
  (общий заголовок направления), не давая метаданным сломать страницу, которая в этом случае сама
  рендерит `SkillDetailError`.
- Навык отсутствует или принадлежит другому направлению → `notFound()`; проверка переиспользует
  существующую `isSkillInCore` из `app/(main)/catalog/[core]/[id]/skill-route.ts`.

Дублирования проверок между `generateMetadata` и страницей избежать нельзя — это два независимых
входа фреймворка; за счёт `cache()` дублируется только дешёвая логика, а не запрос.

### Решение 7. Разметка индексации

- `/profile` и обе `not-found.tsx` → `robots: { index: false, follow: false }` на уровне страницы.
- Существующая логика `app/robots.ts` (полный `disallow` вне production) не меняется: она решает
  другую задачу — закрытие нон-прод стендов целиком.
- `/sign-in` и `/sign-up` остаются индексируемыми — они уже в `sitemap.ts`, это публичные точки
  входа.

`app/not-found.tsx` — Server Component, `export const metadata` в нём допустим.

### Решение 8. `sitemap.ts` выводит направления из `SKILL_CORES`

`PUBLIC_SITEMAP_PATHS` переписывается: `/`, `/sign-in`, `/sign-up`, `/catalog` плюс
`SKILL_CORES.map((core) => \`/catalog/${core}\`)`. Тип `PublicSitemapPath`сохраняется.
Приоритеты:`/`— 1,`/catalog` и направления — 0.8, auth-маршруты — 0.5.

Страницы отдельных навыков в карту сайта не добавляются: их список требует запроса к БД в
`sitemap.ts`, что выходит за scope этого change.

### Решение 9. Ребрендинг — замена строк, а не введение конфигурируемого бренда

`BRAND_NAME` — константа в коде, а не значение из env. Её читают метаданные, `manifest.ts`,
aria-label логотипа и текст PWA-баннера.

_Почему не брать бренд из env:_ метаданные не должны молча разъезжаться между стендами при
неверно заполненной переменной, а `.env` не коммитится.

_Почему `NEXT_PUBLIC_APP_NAME` не подставляется в метаданные:_ вопреки названию, это идентификатор
стенда, а не имя продукта. `src/constants/env.ts` сравнивает его со строкой-константой, вычисляя
`isProductionApp`, от которого зависит `app/robots.ts`, а `next.config.ts` передаёт его как имя
Sentry-проекта. Поэтому метаданные читают `BRAND_NAME`, а переменная продолжает играть свою роль.

_Переименование идентификатора стенда:_ сравнение с унаследованной от прежнего проекта строкой
заменяется на `'starskills'`. Значение выносится в именованную константу `PRODUCTION_APP_NAME`
рядом с `isProductionApp`, чтобы сравнение не было «магической строкой» и чтобы следующее
переименование стенда правилось в одном месте.

Это единственное изменение в change, требующее действия вне репозитория: переменная окружения
production-стенда должна получить значение `starskills` в том же релизе. При рассинхроне
`isProductionApp` становится `false` и `app/robots.ts` отдаёт `Disallow: /` на весь production —
отказ тихий и обнаруживается только по падению индексации. Поэтому в `.env.example` локальное
значение задаётся как `starskills-local`: локальный стенд не должен случайно совпасть с
production-идентификатором.

## Risks / Trade-offs

- **`generateMetadata` на динамических маршрутах конфликтует с `cacheComponents` и ломает
  `npm run build`** → Все затронутые страницы уже некешированно ходят в данные, поэтому шага в
  runtime-режим не происходит. Проверяется реальным `npm run build` в задачах верификации; если
  ошибка `blocking-prerender-metadata-*` всё же возникает, применяется описанный в документации
  `DynamicMarker` на конкретной странице, а не глобальное отключение streaming metadata.
- **Удвоение запросов к бэкенду на страницах навыка** → React `cache()` в репозитории плюс
  явный unit-тест, считающий обращения к SDK-слою за один запрос страницы.
- **`lang="en"` → `lang="ru"` меняет поведение браузерных эвристик (перевод, шрифты, переносы) и
  может сломать существующие снапшоты/E2E** → Изменение точечное, прогоняется полный
  `npm run test` и E2E; риск принимается, текущее значение просто неверно.
- **Ребрендинг ломает существующие тесты бренда** → Тесты обновляются в рамках этого же change;
  файлы перечислены в `proposal.md → Impact`.
- **Расхождение SEO-строк направлений с данными БД** → Осознанный trade-off (Решение 5);
  типизация не даёт забыть новое направление, расхождение текста ловится ручной проверкой.
- **Неверный `NEXT_PUBLIC_FRONT_URL` на стенде даёт канонические адреса на чужой домен** →
  Переменная уже обязательна и уже используется `robots.ts`/`sitemap.ts`; новых способов ошибиться
  не появляется, но ручная проверка `view-source` на стенде обязательна.
- **Streaming metadata: на динамических страницах метатеги могут попасть после `<body>` для
  JS-исполняющих ботов** → Поведение Next.js по умолчанию, HTML-ограниченные боты получают теги в
  `<head>`. Не меняем `htmlLimitedBots`, чтобы не терять TTFB.

## Migration Plan

Миграции данных и изменения API-контракта отсутствуют.

1. Добавить `src/seo/` и обернуть репозитории в `cache()` — изменения без внешнего эффекта.
2. Обновить корневой layout (`metadataBase`, шаблон, OG-база, бренд, `lang`) и `manifest.ts`.
3. Добавить метаданные по маршрутам, включая динамические.
4. Обновить `sitemap.ts` и `.env.example`.
5. Обновить затронутые тесты бренда, добавить новые тесты.
6. Верификация: `npm run tsc`, `npm run lint`, `npm run test`, `npm run build`, ручная проверка
   `view-source`, `/robots.txt`, `/sitemap.xml`, `/manifest.webmanifest`.

**Откат:** revert коммита. Персистентного состояния нет; единственный внешний след — уже
проиндексированные поисковиком заголовки, которые вернутся к прежним при следующем обходе.

## Test strategy

- **Static**: `npm run tsc` (в том числе исчерпывающность `Record<SkillCore, CoreSeoCopy>`),
  `npm run lint`, `npm run fmt:check`, `npm run build` — сборка подтверждает совместимость
  `generateMetadata` с `cacheComponents`.
- **Unit** (`*.unit.test.ts`, Node-окружение): `buildPageMetadata` (canonical, OG/Twitter,
  `noIndex`), `absoluteUrl`, полнота SEO-реестра направлений, содержимое `sitemap()` (наличие
  реальных auth-маршрутов, каталога и всех направлений, отсутствие `/profile`), `robots()` без
  изменений поведения.
- **Component**: не применяется — метаданные не попадают в DOM тестируемого компонента; тесты
  уровня компонентов ограничиваются обновлением существующих проверок бренда.
- **Integration**: не выделяется отдельным уровнем; связка «метаданные + данные» проверяется
  unit-тестом дедупликации (подсчёт обращений к замоканному SDK-слою при последовательном вызове
  `generateMetadata` и загрузки страницы).
- **E2E (Playwright, `src/tests/e2e/`)**: проверка `<title>`, `meta[name="description"]`,
  `link[rel="canonical"]` и `meta[name="robots"]` на `/`, `/catalog`, `/catalog/frontend`,
  странице навыка, `/profile` и 404; проверка доступности и содержимого `/sitemap.xml`.
- **Performance**: отдельных тестов нет; риск удвоения запросов закрывается unit-тестом
  дедупликации.
- **Manual**: `view-source` ключевых страниц, `/robots.txt`, `/sitemap.xml`,
  `/manifest.webmanifest`, предпросмотр ссылки во внешнем OG-валидаторе.

## Open Questions

- Точные маркетинговые формулировки `description` для направлений и главной страницы —
  согласуются с продуктом. Не влияют на структуру спеки, набор задач и подход: строки
  правятся в одном файле `src/seo/cores.ts` без изменения кода маршрутов.
