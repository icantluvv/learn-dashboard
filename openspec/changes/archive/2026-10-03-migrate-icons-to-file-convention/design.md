## Context

См. `proposal.md` — Why. Текущее размещение: `public/favicon.ico` (мультиразмерный ICO, 16x16 и
32x32), `public/apple-touch-icon.png` (180x180), `public/icon-192.png`, `public/icon-512.png`,
`public/icon.png` (1024x1024, не используется в коде — источник для регенерации, этот change его
не трогает), `public/icon.svg` (логотип, используется в `src/components/navigation/logo.tsx`, не
favicon — этот change его не трогает). Ручные `<link>`-теги собираются в `app/layout.tsx` через
`metadata.icons`; `app/manifest.ts` формирует Web App Manifest с собственным массивом `icons`.

Прямого доступа к `node_modules/next/dist/docs` в этой сессии нет (permission denied), поэтому
поведение file-convention подтверждено веб-поиском по официальной документации Next.js
(`nextjs.org/docs/app/api-reference/file-conventions/metadata/app-icons` и
`.../guides/progressive-web-apps`), а не прямым чтением установленной версии. Перед тем как
считать задачу закрытой, нужно подтвердить фактическое поведение локальным `npm run build` и
осмотром сгенерированного `<head>` (хеш в `href`) — см. tasks.md.

## Goals / Non-Goals

**Goals:**

- Избавиться от ручного перечисления иконок в `metadata.icons`, передав эту ответственность
  file-convention файлам (`app/icon.png`, `app/apple-icon.png`, `app/favicon.ico`), которые
  Next.js хеширует автоматически при каждой сборке.
- Решить конкретный воспроизведённый баг: Safari на iOS показывает старый `apple-touch-icon`
  после обновления файла, потому что URL не меняется.
- Зафиксировать это поведение как проверяемое требование в spec `pwa-install` (см. delta spec),
  чтобы регресс обнаруживался тестом, а не вручную на проде.

**Non-Goals:**

- Решение той же проблемы для иконок внутри `app/manifest.ts` (`icon-192.png`, `icon-512.png`,
  `maskable`-иконка). Web App Manifest — статичный JSON/объект с фиксированными путями; Next.js не
  хеширует строки внутри `icons[].src` файл-конвенцией — это свойство относится только к
  `<link>`-тегам, которые Next генерирует из файлов в `app/`. Если кэширование Android/Chrome
  install-flow станет отдельной проблемой, это отдельный change (например, версионирование имени
  файла или собственный route handler для манифеста).
- Замена или ресайз самого изображения иконки — используется то же актуальное изображение, что
  уже лежит в `public/apple-touch-icon.png` и `public/icon-512.png`.
- Миграция `favicon.ico`/`icon.png`/`icon.svg`, не участвующих в баге (логотип в `logo.tsx`
  остаётся на `/icon.svg` в `public/`, это не favicon-конвенция).

## Decisions

- **`app/apple-icon.png` вместо правки `metadata.icons.apple`**: это единственный способ получить
  автоматический хеш в `href`, который и является причиной бага. Альтернатива — вручную добавлять
  версию/query-параметр к пути в `public/` при каждом обновлении иконки — отклонена: это ручной,
  легко забываемый шаг, который change должен устранить, а не формализовать.
- **`app/favicon.ico` переносится вместе с apple-icon, а не оставляется в `public/`**: раз меняем
  модель для одного файла favicon-семейства, логично привести оба классических файла
  (`favicon.ico`, `apple-touch-icon.png`) к единой file-convention модели — иначе в репозитории
  останутся два разных способа объявления favicon без явной причины.
- **`app/icon.png` добавляется как копия `public/icon-512.png`**, а не как новый уникальный
  дизайн: задача — унифицировать механизм кэш-инвалидации, а не менять визуал. Используется самый
  крупный существующий PNG, чтобы `<link rel="icon">` оставался чётким на высоких DPI.
- **`app/manifest.ts.icons` не трогаем**: подтверждено документацией (см. Context) — манифест
  требует стабильных путей фиксированных размеров по спецификации Web App Manifest, а Next.js не
  документирует хеширование путей внутри `manifest.ts`. Попытка указать туда `/icon?<hash>`
  вручную была бы хрупкой (хеш генерируется Next.js во время сборки `<head>`, а не доступен как
  публичный helper для использования в `manifest.ts`).
- **Удаление `public/apple-touch-icon.png` и `public/favicon.ico` после переноса**, а не
  сохранение дубликатов: оставление обоих путей создало бы риск, что кто-то продолжит ссылаться на
  старый нехешированный путь (например, вручную в будущем PR), воспроизведя тот же баг.

## Risks / Trade-offs

- [Предположение о поведении Next.js не проверено прямым чтением docs установленной версии, только
  веб-поиском] → Проверить локальным `npm run build` + осмотром `.next`/отрендеренного `<head>`,
  что `href` действительно содержит хеш для `apple-icon` и `icon`; если поведение отличается —
  откатить и зафиксировать фактическое поведение в proposal/design перед повторной попыткой.
- [`app/manifest.ts.icons` продолжает кэшироваться по старым правилам] → Явно задокументировано
  как Non-Goal и как отдельное известное ограничение в spec; не маскируется как «решено».
- [Существующий E2E-тест `src/tests/e2e/pwa.spec.ts` жёстко ожидает `/apple-touch-icon.png`] →
  Тест обновляется в рамках tasks.md на чтение фактического `href` из HTML, а не константы.

## Test strategy

- **Static**: `npm run tsc`, `npm run lint`, `npx oxfmt` на изменённых файлах.
- **E2E**: обновлённый `src/tests/e2e/pwa.spec.ts` проверяет, что `<link rel="apple-touch-icon">`
  и `<link rel="icon">` отдают реальные изображения по фактическому `href`, и что `href` содержит
  query-параметр (хеш), а не является статичной строкой.
- **Manual**: один прогон `npm run build && npm run prod`, осмотр `<head>` в браузере — убедиться,
  что `href` иконок содержит хеш и значения меняются при изменении содержимого файла (временно
  заменить пиксель в `app/icon.png` и проверить, что хеш в `href` изменился после пересборки).
- Component-тесты не нужны — изменение не затрагивает React-компоненты с интерактивным поведением.
