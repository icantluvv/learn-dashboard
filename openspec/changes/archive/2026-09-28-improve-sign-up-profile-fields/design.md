## Context

Мотивация описана в `proposal.md`. Сейчас `SignUpForm` передаёт обычный объект в server action,
поле `image` валидируется как URL и записывается Better Auth в текстовую колонку `user.image`.
Профиль из `GET /api/me` затем передаёт это значение компонентам `next/image`. PostgreSQL доступен
серверу через общий `pg.Pool`; auth-таблицы закрыты deny-all RLS для `anon` и `authenticated`.

Файловая форма должна соответствовать принятому ADR: multipart обрабатывается серверной границей.
Фактический source of truth API — `api/src/openapi.yaml` (OpenAPI 3.0.2), а `packages/api` генерируется
Kubb 4. Это расходится с описанием OpenAPI 3.2/Hey API в корневых инструкциях, поэтому дизайн
опирается на исполняемые конфиги, которым сами инструкции отдают приоритет.

## Goals / Non-Goals

**Goals:**

- хранить загруженный аватар в PostgreSQL без base64 внутри профиля или cookie/session payload;
- сохранить поле `image` как URL для совместимости существующих потребителей;
- одинаково ограничить новые регистрации двумя значениями пола на клиенте и сервере;
- проверить файл до создания пользователя и обеспечить компенсирующую очистку при сбое записи;
- безопасно и кэшируемо отдавать неизменяемое изображение через same-origin URL.

**Non-Goals:**

- редактор, crop/resize, перекодирование или оптимизация изображения;
- изменение аватара после регистрации;
- перенос аватаров во внешнее object storage/CDN;
- принудительное преобразование уже сохранённого значения пола `other`;
- приватные ACL для аватаров: изображение считается публичной частью профиля, а его UUID —
  непрогнозируемым адресом.

## Decisions

### 1. Dropzone остаётся route-local компонентом на нативном file input

Создать компонент рядом с `/sign-up`, использующий `<input type="file">`, label/button и
drag-and-drop события. Он принимает один файл, объявляет `accept="image/jpeg,image/png,image/webp"`,
показывает object URL preview и освобождает его при замене/unmount. Клавиатурный выбор файла и
нативный input остаются базовой доступной границей.

Отдельная dropzone-библиотека не нужна: сценарий однофайловый, а новая зависимость увеличила бы
bundle и поверхность поведения без пользы.

### 2. Регистрация принимает `FormData`

Форма формирует `FormData` с текстовыми полями и необязательным `avatar`. Server action принимает
неструктурированный вход, нормализует строковые значения и файл, затем валидирует общий объект.
Клиент выполняет лёгкую проверку размера/MIME для быстрого feedback; сервер повторяет размер,
разрешённый MIME и magic bytes JPEG/PNG/WebP до вызова Better Auth.

Сериализация файла в data URL отклонена: base64 увеличивает объём примерно на треть и заставляет
таскать байты через `GET /api/me`, React Query и RSC hydration.

### 3. Бинарные данные хранятся отдельно от `user`

Миграция создаёт таблицу `user_avatar`:

- `id uuid primary key` — генерируется приложением до регистрации;
- `user_id text not null unique references "user"("id") on delete cascade`;
- `content_type text not null` с CHECK для JPEG/PNG/WebP;
- `byte_length integer not null` с CHECK `1..5242880`;
- `data bytea not null`;
- `created_at timestamptz not null default now()`.

Для таблицы включается RLS и deny-all policy для `anon`/`authenticated`; чтение и запись идут
только через server-side `pg.Pool`. Хранение в `user.image` отклонено из-за большого текстового
payload и смешения бинарных данных с auth-моделью. Supabase Storage пока не используется, потому
что требование явно задаёт БД и проект уже имеет прямое server-side соединение.

### 4. `user.image` хранит immutable URL

Перед вызовом Better Auth сервер генерирует UUID аватара и передаёт в `image` путь
`/api/avatars/<uuid>`. После успешного `signUpEmail` он вставляет строку `user_avatar`, связанную с
ID созданного пользователя. Без файла поле `image` не передаётся.

Если вставка аватара завершается ошибкой, сервер удаляет созданного этой попыткой пользователя;
каскад удаляет account/session, а выданная cookie становится недействительной. Ошибка регистрации
возвращается пользователю как общая. Компенсация применяется только к ID, полученному от текущего
успешного `signUpEmail`, поэтому существующий пользователь при конфликте email не затрагивается.

Полноценная общая транзакция отклонена: Better Auth управляет собственными запросами и не принимает
внешний `pg` transaction client. Предварительная загрузка draft-файла добавила бы токены, TTL и
очистку сирот для одношаговой формы.

### 5. Аватар выдаётся отдельным route handler без generated SDK

`GET /api/avatars/[avatarId]` валидирует UUID, читает только `data`, `content_type` и
`byte_length`, возвращает `404` при отсутствии и выставляет:

- сохранённый `Content-Type`;
- точный `Content-Length`;
- `X-Content-Type-Options: nosniff`;
- `Cache-Control: public, max-age=31536000, immutable`.

UUID меняется вместе с содержимым, поэтому immutable-кэш не устаревает. Endpoint загружается
нативно браузером через `<img>`/`next/image` и не включается в generated SDK: текущий общий client
безусловно вызывает `response.json()` для успешных ответов и не поддерживает бинарный `image/*`.
В OpenAPI уточняются description и same-origin example существующего `AuthMe.image`; schema
остаётся `string` с `format: uri`. Сервер строит абсолютный URL от валидированного
`BETTER_AUTH_URL`, поэтому generated `z.url()` остаётся совместимым, а hostname соответствует
текущему окружению.

### 6. Допустимые значения регистрации отделяются от legacy-типа

Ввести константу допустимых значений новой регистрации `['male', 'female']`. UI options и схемы
регистрации строятся из неё. Текущий DB CHECK и тип чтения профиля могут временно сохранять
`other`, чтобы изменение не ломало существующие строки; создать новое значение `other` через
регистрацию становится невозможно. Отдельная миграция данных и сужение DB CHECK возможны после
проверки production-данных и не входят в этот change.

## Risks / Trade-offs

- [Компенсация не равна транзакции и может не выполниться при потере соединения] → логировать сбой
  без персональных данных, сделать cleanup идемпотентным и добавить проверяемый запрос сирот для
  operational runbook.
- [PostgreSQL разрастается от бинарных данных] → лимит 5 MiB, один аватар на пользователя и
  отдельная таблица позволяют позже перенести storage без изменения профильного URL-контракта.
- [MIME заголовок можно подделать] → сверять magic bytes и разрешать только JPEG/PNG/WebP; SVG и
  произвольные active formats не принимать.
- [Публичный URL доступен любому, кто его получил] → использовать криптографически случайный UUID и
  не включать user ID; это соответствует текущему публичному отображению аватара.
- [Object URL предпросмотра может утечь] → всегда вызывать `URL.revokeObjectURL` при замене и
  размонтировании.

## Migration Plan

1. Применить additive-миграцию `user_avatar` до выкладки приложения.
2. Выложить route handler чтения и серверные helpers.
3. Выложить обновлённую регистрацию и OpenAPI/generated client одновременно.
4. Выполнить регистрацию без аватара и с каждым разрешённым форматом, проверить `/api/me` и URL
   изображения.
5. При откате вернуть приложение на прежнюю форму; таблицу оставить неиспользуемой. Удалять её
   только отдельной миграцией после резервного копирования или подтверждения, что данные не нужны.

## Test strategy

- **Static:** OpenAPI lint/bundle, проверка отсутствия смыслового diff после Kubb generation, root
  TypeScript, Oxlint, Oxfmt и production build.
- **Unit:** парсинг multipart-полей, границы 5 MiB, MIME/magic-byte validator, gender schema,
  успешная запись и компенсирующая очистка action, ответы avatar route `200/404` и заголовки.
- **Component:** ровно два option пола; выбор кликом и drop, preview/remove; ошибки типа/размера;
  отправка без файла и с typed `File` fixture. Реальный backend из Vitest не вызывается.
- **E2E:** критический happy path регистрации с PNG и последующее отображение после перезагрузки;
  ключевой negative path с недопустимым файлом и отсутствием созданного аккаунта.
- **Тестовые данные:** минимальные валидные JPEG/PNG/WebP fixtures, файл ровно 5 MiB, файл на один
  байт больше лимита, текстовый файл с ложным `image/png`, уникальные email и очищаемые seed rows.
- **Правила frontend-тестов:** Vitest Browser Mode для компонентов, Playwright fixtures проекта для
  E2E, role/label locators, web-first assertions и обязательные Allure labels соответствующего
  слоя.
- **Manual:** проверить системный file picker, drag-and-drop и качество preview в Chromium; после
  перезагрузки убедиться, что изображение действительно загружается отдельным HTTP-запросом.
