## Why

В мобильной нижней навигации гостевая вкладка сейчас — просто ссылка «Войти» на `/sign-in`, без
подсветки активного состояния и без отдельной страницы профиля: авторизованный пользователь видит
попап, а не полноценный экран аккаунта. Одновременно страницы `/sign-in` и `/sign-up` рендерятся
внутри общего `Layout`, поэтому на мобильной ширине нижняя навигация перекрывает форму входа/
регистрации — эти страницы не должны показывать общую навигацию вовсе. Нужно объединить вкладку
профиля/входа в единую именованную вкладку «Аккаунт» с собственной страницей и изолировать layout
auth-страниц от остального приложения.

## What Changes

- В мобильной нижней навигации вкладка «Войти» заменяется вкладкой «Аккаунт», ведущей на новую
  страницу `/profile` (а не на `/sign-in` напрямую).
- Иконка вкладки «Аккаунт» подсвечивается как активная (тем же способом, что и остальные вкладки
  `NAV_LINKS`), когда текущий маршрут — `/profile`.
- Добавляется страница `/profile`:
    - Страница — Server Component (SSR): выполняет prefetch запроса `auth me` на сервере
      (`getAuthMeQueryOptions`) и гидрирует TanStack Query кэш через `dehydrate`/`HydrationBoundary`,
      чтобы клиентский компонент не делал повторный запрос при первой отрисовке.
    - Внутри SSR-обёртки — клиентский компонент-обёртка (wrapper), который вызывает
      сгенерированный хук `useGetAuthMe` и в зависимости от `isLoading`, `isError` и `data`
      показывает один из вынесенных в отдельные компоненты экранов: загрузка, ошибка, гостевой
      экран или экран авторизованного профиля.
    - Гостевой экран: текст-приглашение войти в профиль и две кнопки — «Войти» (`/sign-in`) и
      «Регистрация» (`/sign-up`).
    - Экран авторизованного пользователя показывает данные профиля (то же содержимое, что сейчас в
      попапе профиля — имя, email, аватар, выход).
- Страницы `/sign-in` и `/sign-up` перестают использовать общий `Layout` (шапку и мобильную нижнюю
  навигацию). Обе страницы переносятся в новую route group `(auth)`, у которой собственный layout
  без `Header`/`BottomNav`; сами URL (`/sign-in`, `/sign-up`) не меняются.
- **BREAKING** для внутренних потребителей: прямая гостевая ссылка «Войти» в нижней навигации
  (`ProfileTab`) удаляется — вход и регистрация для мобильной навигации теперь доступны только через
  `/profile`.

## Capabilities

### New Capabilities

- `profile-page`: страница `/profile` — SSR-обёртка с prefetch `auth me`, клиентский компонент,
  выбирающий экран по `isLoading`/`isError`/`data`, и содержимое каждого экрана (гость, ошибка,
  загрузка, авторизованный профиль).
- `app-header`: вкладка «Аккаунт» в мобильной нижней навигации (замена вкладки «Войти»), переход на
  `/profile`, подсветка активного состояния вкладки при нахождении на `/profile`.

### Modified Capabilities

- `auth-pages`: страницы `/sign-in` и `/sign-up` рендерятся без общего `Header`/`BottomNav`
  (изолированный layout auth-группы маршрутов).

## Impact

- Код: `src/components/bottom-nav/profile-tab.tsx`, `src/components/bottom-nav/profile-tab-slot.tsx`,
  `src/components/navigation/nav-links.ts` (или отдельная логика активности для `/profile`),
  `app/layout.tsx` (перестаёт рендерить `Layout` напрямую), новый `app/(main)/layout.tsx` (рендерит
  `Layout` с `Header`/`BottomNav`) — под него переносятся `app/(home)/`, `app/catalog/` и новая
  страница `app/(main)/profile/page.tsx` (+ `_components/`); перенос `app/sign-in/` и `app/sign-up/`
  под `app/(auth)/sign-in/` и `app/(auth)/sign-up/` с новым `app/(auth)/layout.tsx` без общей
  навигации. Технические причины такого разделения — в `design.md`.
- API/контракт: не затрагивается — используется существующий `GET /api/me`
  (`getAuthMeQueryOptions`, `useGetAuthMe` из `@repo/api`).
- Тесты: component-тесты для экранов страницы профиля (гость/ошибка/загрузка/авторизован) и для
  подсветки активной вкладки «Аккаунт»; unit-тест при необходимости изменения логики активного
  маршрута; E2E — переход по вкладке «Аккаунт» на `/profile` и обратный переход «Войти»/
  «Регистрация» без нижней навигации на экране.
- Зависимости: новых npm-пакетов не требуется.

## Quality impact

- **Уровень риска**: P1. Затрагивает навигацию и вход/регистрацию на всех мобильных маршрутах, но
  не меняет контракт API и не касается платежей или данных.
- **Затронутые маршруты**: `/profile` (новый), `/sign-in`, `/sign-up` (новый layout), мобильная
  нижняя навигация на всех маршрутах.
- **Затронутые компоненты**: `BottomNav`, `ProfileTab`/`ProfileTabSlot`, `Layout`, новая
  `app/(auth)/layout.tsx`, новая страница `app/profile/`.
- **Затронутые API**: нет новых; используется существующий `useGetAuthMe`/`getAuthMeQueryOptions`.
- **Требуемые уровни тестов**: component-тесты для экранов `/profile` и подсветки вкладки; E2E для
  сквозного мобильного пути «Аккаунт → /profile → Войти/Регистрация» и обратно.
- **Ручные проверки**: визуальная проверка, что на `/sign-in` и `/sign-up` нижняя навигация и шапка
  отсутствуют на мобильной ширине; проверка, что SSR-prefetch не даёт лишнего клиентского запроса
  при первой отрисовке `/profile` (Network: нет повторного `GET /api/me` сразу после гидрации).
- **Откат**: изменение изолировано в слое компонентов/страниц; откат — revert коммита, схема БД,
  env-контракт и generated API не затрагиваются.
