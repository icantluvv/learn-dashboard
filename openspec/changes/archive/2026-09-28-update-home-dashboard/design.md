## Context

`Dashboard` (`app/(main)/(home)/_components/dashboard/dashboard.tsx`) — client-компонент,
рендерящийся внутри `page.tsx`, который прогревает `getSkillsQueryOptions` на сервере через
`getSkills()` и гидрирует React Query на клиенте. Текущий компонент не знает о пользователе вовсе.
Аутентификация уже реализована в двух слоях:

- Server: `getCurrentUser()` (`src/lib/auth/get-session.ts`, `server-only`, `cache()`-обёрнут) читает
  сессию Better Auth через `headers()` и возвращает `{ id, name, email, ... } | null`.
- Client: `useCurrentUser(initialUser)` (`src/components/auth-status/use-current-user.ts`) берёт
  `initialUser` как SSR-заглушку и уточняет его через `useGetAuthMe()` — тот же паттерн, что уже
  использует `AuthStatusSlot`/`profile-popover`.

`DIFFICULTY_OPTIONS` (`src/constants/difficulty-options.ts`) используется не только в дашборде, но и
в `app/(main)/catalog/_components/sidebar-filters/difficulty-select.tsx`, поэтому константа
остаётся — убирается только её использование в `Dashboard`.

`app/globals.css` уже содержит слой `:root` с HEX/oklch токенами и `@theme inline` с `--color-*`
alias'ами, которые транслируются в Tailwind utility classes (`bg-...`, `text-...`). Новые токены
должны следовать этому же паттерну.

## Goals / Non-Goals

**Goals:**

- Передать актуальное имя пользователя на страницу дашборда без дополнительного network waterfall
  на клиенте (переиспользовать существующий SSR→CSR паттерн `getCurrentUser`/`useCurrentUser`).
- Оставить `StatCard` переиспользуемым компонентом, расширив его API, не создавая дублирующий
  компонент.
- Ввести 3 новых цветовых токена как часть общей системы токенов проекта (`:root` + `@theme inline`
  alias), а не как хардкод-HEX в компонентах.
- Мини-диаграмма — чисто декоративный, лёгкий SVG-элемент без графической библиотеки и без
  зависимости от реальных временных рядов (данных для помесячной динамики в API нет).

**Non-Goals:**

- Не вводится новая система тем/dark-mode для новых токенов (проект тёмную тему не использует).
- Не добавляется анимация чисел, real-time обновление статистики или графики с реальными данными.
- Не меняется API `getSkills`/`useGetSkills` и его контракт.
- Не переиспользуется `DIFFICULTY_OPTIONS`-рендеринг в другом месте главной страницы (полностью
  убирается с этой страницы).

## Decisions

### 1. Приветствие через клиентский `auth/me` запрос (без серверного прогрева)

`Dashboard` вызывает `useCurrentUser(null)` (`#/components/auth-status/use-current-user`) — тот же
хук, что уже использует `AuthStatus`, но без переданного `initialUser`: сессия целиком приходит из
клиентского TanStack Query хука `useGetAuthMe()` внутри `useCurrentUser`, без отдельного вызова
`getCurrentUser()`/`HydrationBoundary` в `page.tsx`. Это осознанное решение: главная страница не
прогревает `auth/me` на сервере (в отличие от `AuthStatusSlot` в layout, где прогрев уже есть и
кэш переиспользуется через общий `queryKey`), поэтому первый рендер до ответа `useGetAuthMe`
показывает нейтральное «Добро пожаловать», а после ответа — уточняется при наличии сессии.

Импорт `useCurrentUser` — deep import (`#/components/auth-status/use-current-user`), а не через
барrel `#/components/auth-status`: барrel реэкспортирует `AuthStatusSlot`, server-only компонент,
и его протягивание в client-компонент `Dashboard` ломает сборку/тесты (server-only-код в client
бандле).

Альтернатива — прогревать `auth/me` в `page.tsx`, как это делает `AuthStatusSlot` в layout — была
отклонена: `AuthStatusSlot` уже прогревает тот же `queryKey` на каждой странице (он рендерится в
`Header` в layout), поэтому повторный прогрев в `page.tsx` дашборда избыточен, а логика получения
сессии по требованию должна оставаться полностью клиентской для этого компонента.

### 2. Текст приветствия и запасной вариант

Формат — `` `С возвращением, ${name}` `` для авторизованных и статичное «Добро пожаловать» для
неавторизованных. Если `currentUser` существует, но `name` окажется пустой строкой (не ожидается по
модели `CurrentUser`, где `name: string` обязательно и заполняется при регистрации), используется тот
же fallback «Добро пожаловать», чтобы избежать «С возвращением, » без имени.

### 3. Удаление карточек сложности без изменения `computeCatalogStats`

`byDifficulty` остаётся в `computeCatalogStats`/`CatalogStats`, потому что это чистая, покрытая
unit-тестами утилита без другого потребителя проблем не создаёт, а её урезание — это отдельный,
не требуемый в этой задаче рефакторинг (см. AGENTS.md: не расширять diff сверх задачи). В
`Dashboard` просто убирается блок рендера `DIFFICULTY_OPTIONS.map(...)`, импорт
`DIFFICULTY_OPTIONS` в `dashboard.tsx` удаляется как теперь неиспользуемый.

### 4. Редизайн `StatCard`: иконка + декоративная мини-диаграмма

`StatCard` получает два новых **опциональных** пропа:

- `icon: LucideIcon` — рендерится в круглом бейдже (`bg-brand-soft`, `text-brand-primary`) слева от
  текста, как на референсе.
- `sparkline?: number[]` — короткий массив относительных величин (4–6 точек), рендерится как
  маленький inline SVG (столбики или точки-линия) декоративным блоком.

Иконки — `lucide-react` (уже в зависимостях `package.json`, уже фактически часть дизайн-системы
проекта). Выбор на карточку: `Layers`/`BookOpen` — «Навыков», `Boxes`/`FolderTree` — «Тем»,
`ListChecks`/`HelpCircle` — «Вопросов» (финальный выбор — на этапе реализации, по вкусу с
референсом).

Данных для настоящей динамики (истории значений во времени) API не отдаёт, поэтому sparkline
строится детерминированно из текущего значения метрики (например, нормализованная псевдо-серия на
основе `value`), а не мок-рандома — чтобы SSR/CSR рендер совпадал и снапшот-тесты были стабильны.
Диаграмма помечается `aria-hidden="true"`, `role` не устанавливается — вся содержательная информация
уже есть в текстовом `value`/`label` (см. spec: "скрытый от вспомогательных технологий").

Альтернатива — использовать `recharts`/`nivo` для мини-графиков — отклонена: это тяжёлая зависимость
для чисто декоративного статичного элемента без реальных временных данных; чистый inline SVG проще,
меньше и не требует client-only графической библиотеки.

### 5. Новые цветовые токены в `app/globals.css`

В `:root` добавляются:

```css
--brand-primary: #9688e9;
--brand-soft: #e1ddf6;
--brand-ink: #3b3b3b;
```

И в `@theme inline` — Tailwind alias'ы по существующему паттерну (`--color-<token>: var(--<token>)`):

```css
--color-brand-primary: var(--brand-primary);
--color-brand-soft: var(--brand-soft);
--color-brand-ink: var(--brand-ink);
```

Это даёt доступ через `bg-brand-primary`, `text-brand-primary`, `bg-brand-soft`, `text-brand-ink` и
т.д. без хардкода HEX в компонентах, в соответствии с существующей организацией токенов в файле
(`--gray-ultralight`, `--border-shaded` и т.п. используют тот же двухуровневый паттерн).

Именование `brand-*` выбрано (а не `purple-*`/`violet-*`), потому что токены — не универсальная
цветовая шкала, а конкретные брендовые константы под конкретный редизайн (аналогично существующим
семантическим именам `--heading`, `--button-default` в файле).

## Risks / Trade-offs

- [Псевдо-детерминированный sparkline может выглядеть «искусственно» одинаковым для карточек с
  похожими значениями] → приемлемо, так как элемент чисто декоративный и референс тоже использует
  условные, не строго содержательные диаграммы.
- [Удаление `useCurrentUser`-зависимости в `Dashboard` создаёт дополнительный client fetch
  (`useGetAuthMe`) на странице, где раньше его не было] → запрос уже выполняется глобально в layout
  через `AuthStatusSlot`/React Query cache (тот же `queryKey`), поэтому повторный вызов
  `useGetAuthMe` в `Dashboard` переиспользует закэшированный результат, а не создаёт новый
  network-запрос.
- [Существующие тесты/E2E, ссылающиеся на текст «Learn Frontend» или карточки сложности] →
  перечислены в proposal.md Impact; обновляются в рамках tasks.md.

## Test strategy

- Unit: `computeCatalogStats` не меняется — существующий `compute-catalog-stats.unit.test.ts`
  остаётся зелёным без изменений.
- Component (`*.test.tsx`, browser Vitest project): `dashboard.test.tsx` обновляется — проверка
  приветствия для авторизованного/неавторизованного пользователя, подзаголовка «К чему приступим
  сегодня?», отсутствия карточек «Лёгкий/Средний/Сложный», наличия иконки и decorative-диаграммы
  (`aria-hidden`) в `StatCard`. Добавляется/обновляется component test для `StatCard` с новыми
  пропами.
- E2E: точечная проверка `src/tests/e2e/catalog.spec.ts`/`header-nav.spec.ts` на предмет ссылок на
  старый текст главной страницы; при необходимости — правка селекторов, без добавления нового E2E
  сценария (риск P2, достаточно component-покрытия).
- Manual: визуальная проверка в браузере (light theme) — соответствие карточек референсу, отсутствие
  горизонтального скролла на мобильной ширине, проверка что `page.tsx`/`Dashboard` по-прежнему
  корректно работают при ошибке/пустом состоянии (`DashboardError`, `DashboardEmpty` не
  затрагиваются).
