## Context

`app/catalog/[id]/page.tsx` сейчас — заглушка (`async function` без данных, просто печатает `id`).
Контракт `GET /api/skills/{id}` не существует; схема `Skill` (`title` + `questions: string[]`) уже
объявлена в `api/src/components/schemas/Skill.yaml`, но ни один path её не использует. Главная
страница (`app/(home)/page.tsx`) уже задаёт паттерн: `queryClient.query(...)` на сервере +
`<HydrationBoundary state={dehydrate(queryClient)}>` + клиентский компонент, читающий тот же query
через generated hook. См. `proposal.md - Why` для мотивации.

## Goals / Non-Goals

**Goals:**

- Показать заголовок навыка и пронумерованный список вопросов сразу в первом серверном ответе, без
  клиентского JS для рендера контента.
- Переиспользовать существующий паттерн проекта (`queryClient` + `HydrationBoundary`/`dehydrate`,
  тот же generated React Query slice, что и у каталога) вместо отдельного ad-hoc fetch на странице.
- Корректно различить "навык не найден" (`404`) и "запрос не удался" (сеть/`5xx`) — это разные
  requirement'ы в spec.

**Non-Goals:**

- Клиентская интерактивность на странице навыка сверх кнопки "Назад" (избранное, отметка вопроса и
  т.п.) — не в скоупе.
- Реальный backend — контракт и его mock-реализация описаны и проверены только для mock-режима.
- Изменение `GET /api/skills` (список) или связанных фильтров — не затрагивается.

## Decisions

### 1. Почему страница остаётся полностью серверной

**Решение**: `app/catalog/[id]/page.tsx` — `async function` без своего `'use client'`. Данные навыка
получаются один раз через `queryClient.query(getSkillByIdQueryOptions({ id }))` и передаются как
props в дочерние server-компоненты (`SkillDetailContent`, `SkillDetailError`) — не через `useQuery`
на клиенте. Единственное исключение — изолированный клиентский лист `BackButton` (см. Decision 5):
он не участвует в загрузке данных навыка и не превращает страницу в client-компонент.
`<HydrationBoundary state={dehydrate(queryClient)}>` вокруг дерева сохраняется ради единообразия с
`app/(home)/page.tsx` (тот же `getQueryClient()`, тот же generated query key на клиенте, если в
будущем странице потребуется клиентский рефетч), но на старте не гидратирует ни один клиентский
consumer.

**Альтернативы**:

- Обычный `fetch`/generated client-вызов напрямую (`getSkillById()`), без React Query — проще, но
  ломает единообразие: `@repo/api` уже генерирует query hook/query-options для каждой операции, и
  остальной проект получает данные только через этот слой (mock-режим, `x-url` proxy header и т.д.
  завязаны на generated client, а не на прямой `fetch`).
- Клиентский компонент с `useGetSkillById` (как `Catalog` с `useGetSkills`) — соответствовал бы
  паттерну каталога буквально, но добавляет ненужный client bundle и лишний рендер-цикл
  (skeleton → data) на странице без интерактивности, что расходится с прямым запросом пользователя
  отрисовывать всё в SSR.

### 2. Контракт `GET /api/skills/{id}`

**Решение**: новый файл `api/src/paths/api_skills_id.yaml`, путь `/api/skills/{id}` в
`api/src/openapi.yaml`, `operationId: getSkillById`, тег `Skills` (та же группа `skillsController` в
kubb, что и `getSkills`). Обязательный path-параметр `id: string`. Успешный ответ переиспользует
существующую схему `Skill` (`title`, `questions`) — id в теле ответа не дублируется, он уже есть в
URL. `404` — без тела, по аналогии с `api_example.yaml`.

**Альтернативы**:

- Добавить `id` в схему `Skill` и переиспользовать её и для списка, и для деталей — отклонено:
  список (`GetSkills200`) и деталь навыка имеют разный набор полей (список не содержит `questions`,
  деталь не содержит `difficulty`/`topic`/`questionsCount`); объединение схем добавило бы полям,
  ненужным в конкретном ответе, вместо чёткого разделения по операциям.
- Возвращать `404` с телом ошибки (`{ message: string }`) — отклонено ради минимализма: ни один
  существующий path в проекте так не делает (`api_example.yaml` тоже возвращает `404` без схемы),
  фронту достаточно кода статуса, чтобы вызвать `notFound()`.

### 3. Включение mock-режима для `/catalog/*`

**Решение**: `src/mock-mode/config.ts` — `mockModePagePaths` дополнен строкой `/catalog` (было
только `/`). Матчинг в `isMockModePagePath()` использует `startsWith(`${mockPath}/`)`, поэтому одна
запись покрывает и `/catalog`, и `/catalog/{id}`. Обнаружено вручную (см. `tasks.md - 2.3`): без
этой записи `GET /api/skills/{id}` на странице навыка уходил на реальный (в dev — несуществующий)
backend вместо мока, и обе ветки (найден/не найден) заканчивались одинаковой сетевой ошибкой.

**Альтернативы**:

- Регулярное выражение `/^\/catalog(\/|$)/` вместо строки — не нужно: существующий матчер уже
  обрабатывает `startsWith` для строковых путей, точное совпадение с regex ничего не добавляет.

### 4. Различение 404 и прочих ошибок на сервере

**Решение**: generated client (`packages/api/base/client.ts`) на не-`ok` ответ бросает
`new Error(statusText, { cause: { status, ... } })`. `page.tsx` оборачивает
`queryClient.query(...)` в `try/catch`: `cause.status === 404` → `notFound()` (встроенный Next.js
механизм, отдаёт `app/not-found.tsx`); любая другая ошибка → рендер `SkillDetailError` внутри той же
`page-wrapper`-обёртки, без `notFound()`.

**Альтернативы**:

- Полагаться на `queryClient.query(...).catch(() => undefined)` (как делает `app/(home)/page.tsx`) и
  различать случаи по `undefined`-данным на клиенте — не подходит: на клиенте ветвления не будет
  (страница не рендерит `'use client'`-компонент с `isError`/`isPending`), различие нужно сделать
  синхронно на сервере до рендера.

### 5. Кнопка "Назад" как изолированный клиентский лист

**Решение**: `BackButton` — маленький `'use client'`-компонент (`app/catalog/[id]/_components/
skill-detail/back-button.tsx`), использует `useRouter().back()` из `next/navigation` и `Button` из
`@heroui/react` с `variant="ghost"` (без фона и рамки в состоянии покоя — валидные варианты в
проекте: `danger`, `danger-soft`, `ghost`, `outline`, `primary`, `secondary`, `tertiary`;
`variant="light"` из примеров HeroUI-документации в этом проекте не типизирован) и иконкой
`ArrowLeft` из уже используемого в проекте `lucide-react` (см. `Settings` в
`MobileFiltersDrawer`) слева от текста. Рендерится в `page.tsx` перед `SkillDetailContent`,
оборачивающим только заголовок и вопросы — сама страница `page.tsx` остаётся `async`
server-компонентом, `'use client'` есть только у листового компонента.

**Альтернативы**:

- `<Link href="/">` на главную — не подходит: пользователь может прийти на страницу навыка не
  только с несфильтрованного каталога (например, по прямой ссылке или из будущего поиска), а
  `router.back()` возвращает именно туда, откуда он пришёл, включая активные фильтры в URL.
- Ссылка вместо кнопки — отклонено ради единообразия: единственный интерактивный элемент в этом
  UI-паттерне проекта (`ResetFiltersButton`) уже оформлен как `Button` с `onPress`.

### 6. Разделение заголовка и списка вопросов на два визуальных блока

**Решение**: `SkillDetailContent` рендерит не одну `<section>` на весь контент, а две отдельные
белые карточки (`rounded-xl bg-white p-6`) в общем `v-stack gap-4`: первая — только `<h1>` с
`title`, вторая — список вопросов (или сообщение об их отсутствии). Разбивка чисто визуальная, не
меняет `SkillDetailContentProps`, разметку `BackButton` или контракт.

**Альтернативы**:

- Одна секция с внутренним разделителем (`<hr>`/`border-b`) — отклонено: две независимые карточки
  того же визуального языка, что и карточки каталога (`SkillCard`), лучше держат ритм страницы, чем
  один блок с внутренней чертой.

## Risks / Trade-offs

- **[Риск]** Mock-данные вопросов по `id` навыка нужно завести вручную (в `GetSkills200` их сейчас
  нет) → **Митигация**: отдельный `Record<string, GetSkillByIdQueryResponse>` в
  `mock-scenarios.ts`, ключи совпадают с `id` из `skillCards`; не найденный `id` → route возвращает
  `404` через `mock-client`.
- **[Риск]** `HydrationBoundary` без единого клиентского consumer выглядит избыточным кодом →
  **Митигация**: осознанный выбор ради единообразия паттерна данных по проекту (см. Decision 1); при
  появлении интерактивности на странице hydration уже на месте.
- **[Риск]** Реальный backend может не поддерживать точно такой контракт `404` (например, вернуть
  `200` с пустым телом) → **Митигация**: `api/src/paths/api_skills_id.yaml` — источник истины для
  backend-команды.

## Test strategy

- **Unit**: мок-роут `GET /api/skills/:id` в `mock-scenarios.ts` — найденный `id` возвращает
  `title`/`questions`, ненайденный `id` возвращает `404`.
- **Component**: серверные компоненты страницы (`SkillDetailContent` — заголовок + нумерация,
  включая пустой список вопросов; `SkillDetailError` — текст ошибки) рендерятся и проверяются как
  обычные React-компоненты через `vitest-browser-react` (server-компоненты без async-данных внутри
  самого компонента тестируются как обычные функции, принимающие props).
- **Integration/E2E**: не добавляются в это изменение — 404-ветка полагается на встроенный
  Next.js `notFound()`/`not-found.tsx`, который уже используется в проекте для других маршрутов и не
  тестируется отдельно.
- Подробная матрица покрытия — в `test-plan.md`.
