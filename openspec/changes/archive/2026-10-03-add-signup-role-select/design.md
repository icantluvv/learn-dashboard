## Context

Регистрация и профиль построены на better-auth: пользовательские поля сверх базовой схемы
описываются через `user.additionalFields` в `src/lib/auth/server.ts` (`src/lib/auth/database.server.ts`
отвечает за Prisma-адаптер). Форма `/sign-up` — `useAppForm` (`@repo/core/form`) с Zod-валидацией
(`src/modules/auth/schemas.ts`) и статической картой опций select по образцу `gender` (поле `gender`
уже реализовано как pattern для select-поля с enum-значениями). Контракт `GET /api/me` описан в
`api/src/components/schemas/AuthMe.yaml` и генерируется в `packages/api` через Kubb; у better-auth
нет собственного публичного OpenAPI, `/sign-up`/`/sign-in` в контракте не описаны (см. proposal.md).
Страница `/profile` — Server Component с prefetch + клиентский `useGetAuthMe`, экран авторизованного
пользователя — `profile-authenticated.tsx`, сейчас выводит только `name`, `email`, `image`.

## Goals / Non-Goals

**Goals:**

- Добавить `role` как обязательное поле при регистрации и `lastName` как необязательное, по тому же
  паттерну, что уже используется для `gender`; перевести `age` из обязательного в необязательное.
- Прокинуть оба новых поля через весь стек: Zod-схема формы → server action → better-auth
  `additionalFields` → Prisma-модель пользователя → `AuthMe` OpenAPI-схема → `CurrentUser` →
  экран профиля.
- Отобразить роль человекочитаемой строкой на `/profile`, не меняя сырое значение enum в контракте.

**Non-Goals:**

- Не создаётся отдельная страница/форма редактирования профиля — она в проекте пока отсутствует и
  не входит в этот change (см. отчёт исследования: redirect на edit-profile нет нигде в коде).
- Не меняется набор значений `gender` и прочих уже существующих полей формы регистрации.
- Не вводится отдельная роль-based авторизация/права доступа — `role` в этом change носит чисто
  профильный, отображаемый характер.

## Decisions

### 1. `role` как `additionalFields` + Prisma-колонка, а не отдельная таблица

Роль — фиксированный закрытый enum из 4 значений, не ожидается расширение прав на основе неё в
ближайшем будущем. Храним как `role: string` c Prisma-уровня enum/varchar в таблице `user`, по
аналогии с существующим `gender`. Отдельная таблица ролей была бы избыточна для статического списка
без связанных сущностей.

### 2. `lastName` как отдельное необязательное поле, а не часть `name`

Разбиение имени на `name`/`lastName` выбрано вместо одного составного поля, потому что личный
кабинет должен показывать «полное имя» (эта формулировка уже используется в проекте), а раздельное
хранение не теряет информацию и не требует парсинга строки на сервере. UI остаётся прежним — два
соседних текстовых поля, а не одно широкое. Поле необязательно (по требованию) — не у каждого
пользователя обязательно нужно запрашивать фамилию на старте; `name` остаётся обязательным как и
раньше.

### 3. Константы enum по образцу `gender`

`src/lib/auth/constants.ts` получает `ROLE_VALUES = ['developer', 'analyst', 'student', 'beginner']
as const`, а `app/(auth)/sign-up/_constants/role-options.ts` — `ROLE_OPTIONS` с русскими label (по
образцу `gender-options.ts`). Маппинг enum → читаемая строка для профиля размещается рядом с местом
использования на `profile-authenticated.tsx` (небольшой `as const` словарь), а не как новый
shared-модуль — используется только в одном месте.

### 4. Обратная совместимость существующих пользователей

Только `role` объявляется в OpenAPI и better-auth как `required: true` для НОВОЙ регистрации (форма
и server action требуют его всегда); `lastName` и `age` остаются необязательными — Prisma-колонки
для них nullable, миграция данных не нужна, а экран профиля уже обязан корректно работать без этих
значений (см. требование profile-page про отображение полного имени, если фамилия указана). Для
уже существующих в БД пользователей без `role` миграция Prisma добавляет колонку с безопасным
дефолтом (`role = 'beginner'`), затем делает её `NOT NULL`. Отдельного флага «профиль не
дозаполнен» в этом change не вводится.

## Risks / Trade-offs

- [Существующие пользователи получат роль `beginner` по умолчанию без собственного выбора] →
  Задокументировано в proposal.md как **BREAKING** только для `role`; если потребуется точный
  бэкофилл, это отдельный последующий change (например, принудительное дозаполнение профиля). Для
  текущего объёма проекта (dev/pet-проект, прямые коммиты в master) значение по умолчанию допустимо.
- [Рассинхронизация OpenAPI `AuthMe` и Prisma-схемы при ручном редактировании] → Единственный
  источник истины для `AuthMe` — `api/src/components/schemas/AuthMe.yaml`; `packages/api/codegen`
  перегенерируется (`npm --workspace @repo/api run gen`), ручные правки в codegen запрещены
  (AGENTS.md).
- [Жёстко заданный список ролей потребует ещё одного change при добавлении нового варианта] →
  Приемлемо: список фиксирован бизнес-требованием «разработчик/аналитик/студент/начинающий», как и
  `gender` сейчас ограничен двумя значениями при регистрации.

## Migration Plan

1. Обновить `api/src/components/schemas/AuthMe.yaml` (обязательный `role`, необязательный
   `lastName`, `age` переносится в необязательные) → перегенерировать `packages/api` → `npm run tsc`
   для generated output.
2. Добавить Prisma-миграцию: новая nullable-колонка `last_name` (varchar), колонка `role`
   (varchar/enum) с дефолтом `'beginner'` для существующих строк, затем `NOT NULL`; колонка `age`
   становится nullable без изменения дефолта.
3. Обновить `user.additionalFields` в `src/lib/auth/server.ts` и `CurrentUser` в
   `src/lib/auth/get-session.ts`.
4. Обновить форму регистрации, Zod-схемы, server action.
5. Обновить экран `/profile`.
6. Откат: обратная Prisma-миграция удаляет колонки; откат OpenAPI/codegen — git revert коммита с
   регенерацией.
