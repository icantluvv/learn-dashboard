## Context

Мотивация — см. `proposal.md` → «Why». Требования — см. `specs/` этого change.

Текущее состояние, которое формирует подход:

- `app/(home)/page.tsx` — async Server Component: `getQueryClient()`, `getSkills()` в `try/catch`
  (best-effort прогрев), `queryClient.setQueryData(getSkillsQueryOptions().queryKey, skills)`, затем
  `HydrationBoundary` с `<SidebarFilters />` и `<Catalog />` в обёртке
  `page-wrapper v-stack gap-12 md:flex-row`.
- Route-local код каталога полностью самодостаточен внутри `app/(home)/`: ничто за пределами этой
  группы не импортирует её `_components`, `_hooks` или `_constants` (проверено grep).
- `Catalog` — Client Component на `useGetSkills({ params })`, где `params` собираются из
  `useSkillsFilters()` (nuqs) через `toSkillsQueryParams`. Фильтрация выполняется на бэкенде по
  query-параметрам контракта.
- Элемент списка — `GetSkills200[number]` с полями `id`, `title`, `topic`, `difficulty`,
  `questionsCount`. Сгенерированный `Skill` в `packages/api/base/codegen/types/Skill.ts` описывает
  другую (более узкую) форму и для дашборда не годится.
- `DIFFICULTY_LABELS` лежит в `app/(home)/_constants/difficulty-options.ts` и используется
  `SkillCard` и `DifficultySelect`.
- `app/catalog/[id]/` уже существует; `BackButton` использует `router.back()` и на адрес каталога не
  завязан.
- Группа `(home)` — route group без сегмента в URL; кроме `page.tsx` и приватных директорий в ней
  ничего нет (нет `layout.tsx`, `loading.tsx`, `error.tsx`).
- `src/tests/allure-labels.ts` содержит запись про `/app/(public)/(home)/` — путь, которого в
  репозитории нет; к этому change отношения не имеет и не правится.

## Goals / Non-Goals

**Goals:**

- Перенести каталог на `/catalog` буквально один в один: та же разметка, те же компоненты, тот же
  SSR-прогрев, те же тесты — без попутного рефакторинга.
- Дать главной странице содержательный дашборд, не вводя новых эндпоинтов и не меняя
  OpenAPI-контракт.
- Сохранить `app/catalog/[id]` работоспособным и не тронуть его код.

**Non-Goals:**

- Рефакторинг компонентов каталога, фильтров или хука `useSkillsFilters` — переезд без правок логики.
- Новые эндпоинты, агрегирующие показатели на бэкенде.
- Редирект со старых ссылок `/?<фильтры>` на `/catalog?<фильтры>`.
- Навигационные ссылки в шапке — это change `rework-app-header`.
- Персональная статистика пользователя (прогресс, пройденные навыки) — данных для неё в API нет.

## Decisions

### 1. Каталог переезжает в `app/catalog/page.tsx`, группа `(home)` остаётся под дашборд

`app/catalog/` уже существует как директория с `[id]/`. Добавляем в неё `page.tsx` и
`_components/` — детальная страница остаётся во вложенном `[id]/` и не конфликтует.

`app/(home)/page.tsx` остаётся на месте и переписывается под дашборд, `app/(home)/_components/`
наполняется компонентами дашборда. Группу `(home)` не убираем: она уже есть, ничего не стоит и
оставляет место для будущего `layout.tsx` дашборда.

Альтернатива — вынести каталог в route group `(catalog)/catalog/`: отвергнуто, лишний уровень без
пользы, так как у каталога нет собственного layout.

### 2. Перенос файлов через `git mv`

Каталог и фильтры переносятся `git mv`, чтобы история файлов сохранилась и diff читался как
переименование, а не как удаление+добавление. Переносим целиком:

```
app/(home)/_components/catalog/         → app/catalog/_components/catalog/
app/(home)/_components/sidebar-filters/ → app/catalog/_components/sidebar-filters/
app/(home)/_hooks/use-skills-filters.ts → app/catalog/_hooks/use-skills-filters.ts
app/(home)/_hooks/use-skills-filters.unit.test.ts → app/catalog/_hooks/…
app/(home)/_constants/difficulty-options.ts → app/catalog/_constants/difficulty-options.ts
```

Вместе с ними переезжают каталоги `__screenshots__/`. Имена файлов снапшотов содержат имя тест-файла,
а не путь, поэтому переименования не требуют.

После переноса правятся только относительные импорты: `../../_hooks/use-skills-filters` →
`../../_hooks/use-skills-filters` (глубина сохраняется, так как структура уровней та же:
`_components/<группа>/<файл>` → `_hooks`). Это проверяется `npm run tsc`, а не на глаз.

Оговорка: `DIFFICULTY_LABELS` нужен и дашборду (подписи уровней сложности). Дублировать константу
нельзя, а импортировать route-local код одного сегмента из другого — тоже. Поэтому
`difficulty-options.ts` поднимается в shared-слой `src/constants/difficulty-options.ts` и
импортируется обоими сегментами через `#/constants/difficulty-options`. Это ровно тот случай,
который AGENTS.md описывает как «поднимать после появления второго потребителя».

### 3. Дашборд считает показатели на клиенте из того же списка навыков

Дашборд использует `useGetSkills()` без фильтров и агрегирует результат чистой функцией
`computeCatalogStats(skills)` → `{ skillsCount, topicsCount, questionsCount, byDifficulty }`.
Страница `/` прогревает кэш тем же `getSkills()`, что и каталог, так что дополнительного сетевого
запроса при гидратации не возникает и требование «SSR не делает self-fetch» выполняется.

Почему не серверный агрегат в route handler: новый эндпоинт потребовал бы правки OpenAPI-контракта и
регенерации клиента — несоразмерно для четырёх чисел, вычислимых из уже получаемого списка.

Почему не серверное вычисление прямо в `page.tsx` без клиентского хука: тогда состояния загрузки и
ошибки, которые требует спека, пришлось бы выражать иначе, и поведение разошлось бы с каталогом.
Держим тот же паттерн, что у `Catalog`: серверный прогрев + клиентский хук + три состояния.

`computeCatalogStats` — чистая функция в отдельном файле, покрывается unit-тестом без рендера.

### 4. Старые ссылки с фильтрами не редиректим

`/?search=react` после переноса просто откроет дашборд, игнорируя параметры. Редирект не вводим:
приложение не в проде, внешних ссылок на отфильтрованную главную нет, а `redirect` в `page.tsx`
главной по наличию любого query-параметра — хрупкая эвристика (параметры могут появиться от
аналитики или utm).

Это осознанный breaking change, зафиксированный в `proposal.md` → «What Changes».

### 5. Purpose существующих спек правится вручную

`openspec/specs/skills-catalog/spec.md` → `## Purpose` содержит «на главной странице». Delta-файл для
существующей capability не может менять Purpose — он игнорируется при архивации. Поэтому Purpose
правится прямым редактированием главной спеки, отдельной задачей.

## Test strategy

Полная матрица сценарий → уровень → файл — в `test-plan.md`.

- **Static**: `npm run tsc` — главный инструмент проверки корректности переноса: любая незакрытая
  ссылка на перемещённый модуль упадёт здесь. Плюс `npm run lint` и `npx oxfmt` по изменённым файлам.
- **Unit**: `computeCatalogStats` — пустой список, один навык, несколько тем с повторами, уровень
  сложности без навыков, суммирование `questionsCount`. Перенесённый
  `use-skills-filters.unit.test.ts` должен пройти без правок содержимого.
- **Component**: перенесённые `catalog.test.tsx`, `skill-card.test.tsx`,
  `reset-filters-button.test.tsx` должны остаться зелёными без изменений тел тестов — это и есть
  проверка «перенесли один в один». Новые component-тесты для дашборда: показатели по непустому
  каталогу, распределение по сложности, состояния загрузки/ошибки/пустого каталога.
- **Integration**: отдельного уровня нет. Связка «SSR-прогрев → гидратация без повторного запроса»
  наблюдаема только в реальном браузере и закрывается E2E.
- **E2E**: `/catalog` открывается и показывает карточки; фильтр, заданный в UI, попадает в
  query-параметры `/catalog` и переживает перезагрузку; переход «главная → каталог» по ссылке
  дашборда; `/` не содержит сетки карточек.
- **Performance**: не требуется — тот же объём данных, тот же запрос.
- **Manual**: попиксельное сравнение `/catalog` с прежней главной (раскладка, отступы, поведение
  мобильного drawer фильтров), поведение дашборда при пустом и ошибочном ответе.

## Risks / Trade-offs

- **Перенос «один в один» легко нарушить попутными правками** → переносить `git mv` без правок тел
  компонентов; единственные допустимые изменения — пути импортов; перед коммитом прогнать
  `git diff -M --stat` и убедиться, что переименования распознаны, а содержимое не менялось.
- **Снапшот-тесты каталога могут упасть из-за смены окружения рендера** → имена снапшотов не зависят
  от пути, тела тестов не меняются; если падение всё же произойдёт, это сигнал реального изменения
  рендера, а не переноса — разбирать, а не перегенерировать снапшоты вслепую.
- **Подъём `difficulty-options.ts` в `src/constants/`** → расширяет shared-слой; оправдано появлением
  второго потребителя (дашборд), иначе константа дублировалась бы.
- **Дашборд грузит полный список навыков ради четырёх чисел** → приемлемо при текущем объёме
  каталога; при росте потребуется серверный агрегат, что зафиксировано как будущая работа, а не
  часть этого change.
- **Breaking change по URL фильтров** → внешних ссылок нет, приложение не в проде; при
  необходимости редирект добавляется отдельным change.
- **Блокирует `rework-app-header`** → этот change должен быть применён первым; порядок зафиксирован в
  design.md обоих change.

## Migration Plan

Единый коммит в `master`. Порядок работ внутри change:

1. Поднять `difficulty-options.ts` в `src/constants/` и обновить импорты у текущих потребителей —
   изолированный шаг, проверяется `npm run tsc`.
2. `git mv` каталога и фильтров в `app/catalog/`, создать `app/catalog/page.tsx` как копию текущего
   `app/(home)/page.tsx`, поправить импорты, прогнать `tsc` и перенесённые тесты.
3. Переписать `app/(home)/page.tsx` под дашборд, добавить `computeCatalogStats` и компоненты
   дашборда с тестами.
4. E2E и ручные проверки.

Откат — `git revert`; схема БД, env и generated API не затрагиваются. После этого change применяется
`rework-app-header`.
