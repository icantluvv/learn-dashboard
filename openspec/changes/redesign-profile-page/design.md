## Context

См. `proposal.md` — Why. Технические ограничения, важные для реализации:

- `CurrentUser` (`src/lib/auth/get-session.ts`) уже содержит `name`, `lastName?`, `email`, `age?`,
  `role`, `image?`, `completedSkillsCount?` — better-auth `additionalFields`. Менять контракт
  better-auth не требуется.
- Аватар при регистрации сохраняется как бинарные данные в таблице `user_avatar`
  (`src/modules/auth/avatar-repository.server.ts`: `saveAvatar`, `getAvatar`) и отдаётся через route
  `app/api/avatars/[id]`; URL вида `/api/avatars/{id}` записывается в поле `image` пользователя.
  Валидация файла (`src/modules/auth/avatar.ts`: `getAvatarFileError`, `validateAvatarFile`) уже
  реализована и переиспользуется без изменений.
- better-auth предоставляет встроенный `auth.api.updateUser` для изменения `input: true` полей
  текущей сессии (в т.ч. `image`), поэтому отдельный OpenAPI-эндпоинт для обновления профиля не
  нужен — замена аватара реализуется server action'ом, аналогичным `signUpAction`.
- Изученные навыки хранятся в таблице `user_completed_skill (user_id, skill_id)`
  (`src/modules/skills/server/skill-completion-repository.server.ts`); у `Skill` есть поле `core`.
  Сегодня нет запроса, который JOIN'ит эти навыки с направлением для текущего пользователя —
  требуется новая функция выборки.
- `packages/api` codegen не покрывает User/Profile и не должен — профильные данные идут через
  better-auth и server actions, а не через Hey API/Kubb контракт.

## Goals / Non-Goals

**Goals:**

- Переоформить `profile-authenticated.tsx` по референсному макету (баннер, крупный аватар, карточка)
  средствами Tailwind/`@repo/core`, без новых внешних UI-библиотек.
- Дать пользователю заменить аватар без повторной регистрации, переиспользуя существующую валидацию
  и хранилище.
- Показать изученные навыки, сгруппированные по направлению, одним серверным запросом при рендере
  страницы (без дополнительного клиентского запроса поверх уже существующей гидратации `auth me`).

**Non-Goals:**

- Кадрирование (crop) или редактирование изображения перед загрузкой — загружается файл как есть, как
  и при регистрации.
- Редактирование имени, фамилии, возраста, роли или email с этого экрана — это отдельная задача вне
  текущего изменения.
- Пагинация или поиск по изученным навыкам — список по направлению показывается целиком.
- Удаление/сброс аватара в заглушку — только замена на новый файл.

## Decisions

### Замена аватара — server action, а не route handler

Используем Next.js server action (как `signUpAction`), а не отдельный `POST /api/avatars`
route handler. Server action получает `FormData` с файлом, валидирует через `validateAvatarFile`,
сохраняет через `saveAvatar` с новым `id = crypto.randomUUID()`, затем вызывает
`auth.api.updateUser({ headers, body: { image: '/api/avatars/{id}' } })` в контексте текущей сессии.
better-auth сам проверяет наличие сессии и обновляет только поле `image`. Старая запись в
`user_avatar` намеренно не удаляется (нет каскадного кода очистки сегодня) — это согласуется с
Non-Goals и не меняет внешнего поведения.

Альтернатива — отдельный route handler с ручной проверкой сессии через `getCurrentUser()` — отклонена:
server action проще интегрируется с client-компонентом выбора файла (`useActionState`/прямой вызов)
и не дублирует проверку сессии, которую уже делает `auth.api.updateUser`.

### Клиентский триггер загрузки — скрытый `<input type="file">` поверх аватара

Круглый аватар оборачивается в клиентский компонент с визуально скрытым
`<input type="file" accept={AVATAR_ACCEPT}>`, у которого клик по аватару программно вызывает
`input.click()` (или `<label>` оборачивает `<input>` — выбирается при реализации). При выборе файла
компонент сразу вызывает server action (optimistic UI: мгновенно показывает локальный
`URL.createObjectURL` предпросмотр, затем подтверждает реальным `image` после ответа action). Это
единственный интерактивный элемент на экране профиля — отдельная страница/модалка не нужна.

### Группировка изученных навыков — новая функция в существующем skills-репозитории

Добавляется функция в `src/modules/skills/server/skill-completion-repository.server.ts` (или соседний
файл того же модуля), которая JOIN'ит `user_completed_skill` со `skill` по `user_id` текущего
пользователя и группирует результат по `core` на уровне SQL или JS-агрегацией после одного запроса.
Используется на сервере внутри `app/(main)/profile/page.tsx` (Server Component), результат передаётся
пропом в `profile-authenticated.tsx` — без отдельного клиентского query/хука и без изменений в
`packages/api` codegen, так как это не HTTP API, а прямой server-side репозиторий, как и остальные
данные skills-модуля.

### Расположение нового UI-кода

Новые компоненты (аватар с загрузкой, секция навыков по направлениям) размещаются в
`app/(main)/profile/_components/profile-view/` рядом с `profile-authenticated.tsx` — это
route-local UI, используемый только этим экраном (правило "общий код начинайте в самой узкой
области"). Server action для замены аватара размещается в `src/modules/auth/actions.ts` рядом с
`signUpAction`, так как переиспользует тот же модуль валидации/хранилища.

## Risks / Trade-offs

- **Старые записи `user_avatar` не удаляются при замене** → со временем таблица растёт. Митигация:
  вне текущего скоупа; отмечено как Non-Goal, при необходимости — отдельная задача на очистку.
- **`auth.api.updateUser` обновляет `image` как обычное `input: true` поле** → если в будущем
  потребуется запретить прямое изменение `image` через стандартный update-профиля API (если он
  появится), это решение придётся пересмотреть. Митигация: сегодня такого API нет, риск
  гипотетический.
- **Группировка по `core` в JS, если SQL JOIN вернёт плоский список** → при большом количестве
  изученных навыков у одного пользователя это дешёвая операция (сотни строк максимум), риск
  производительности низкий.

## Test strategy

- Static: `tsc`, `lint` — проверка новых server action, типов группировки по `core`.
- Unit: тесты на функцию группировки изученных навыков по направлениям
  (`*.unit.test.ts` рядом с репозиторием) — пустой список, один core, несколько core.
- Component: `profile-authenticated.test.tsx` (browser project) — рендер карточки с баннером,
  условный показ возраста, клик по аватару открывает file input, рендер секции навыков (пусто / с
  группами).
- Integration/manual: сценарий реальной загрузки файла через server action проверяется вручную или
  через Playwright (см. test-plan.md) — валидация форматов, обновление отображаемого фото без
  перезагрузки.
- E2E не требуется для happy path полностью, но файл-аплоад стоит покрыть одним Playwright-сценарием
  P1 (см. test-plan.md), так как затрагивает реальный браузерный file picker.
